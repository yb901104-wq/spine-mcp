## 官方 JSON 文档对照与 curve 维数缺陷（重大发现）

用户提供 [Spine JSON 格式文档](https://zh.esotericsoftware.com/spine-json-format) 作为参考。用户判断：一份文档无法覆盖所有版本，版本间细节差异正常。**该判断成立，已实测确认。**

### 1. 该中文文档是 3.8 口径，与 4.1.24 有硬冲突（项目实现均正确，未盲信文档）

| 项 | 官方中文文档 | 4.1.24 runtime 实际 | 项目 |
|---|---|---|---|
| rotate 关键帧字段 | `angle` | `value`（SkeletonJson.js:972 `getValue(keyMap,"value",…)`；:623 rotate→readTimeline1） | ✅ 用 value |
| 绘制顺序 timeline 名 | `draworder`（全小写） | `map.drawOrder`（:892） | ✅ 用驼峰 |
| curve X 轴单位 | 「单位是帧」 | cx 为 0..1 归一化（readCurve 里 cx 不乘 scale，cy 才乘） | — |

结论：官方文档只能作**字段语义参考**，不能作**写入校验依据**；真正依据是 4.1 runtime 源码 + 当前版本真实样本。项目 `docs/官方JSON规范审查.md` 里「官方文档字段含义 + 4.1.24 样本字段形态双重规则，差异必须记录」的策略是对的。

### 2. 真正的缺陷：curve 在二维 timeline 上必须是 8 元，官方文档完全没写

- runtime `readCurve(curve, …)` 内 `let i = value << 2;` —— `value` 是**维度索引**，二维 timeline 第二维度从 `curve[4]` 起取。
- 实测样本 `xiaoren.json`：rotate 的 curve 恒为 **4 元**，translate/scale/shear 恒为 **8 元**（前 4 给 x、后 4 给 y）。
- 实测后果（bone2 translate，6 个 8 元 curve 截成 4 元）：**41 帧中 40 帧 y 值为 NaN，x 值完全正常、无任何报错**。属静默污染，x 分量正常极具迷惑性。

### 3. 项目侧缺口

`src/spineJson.ts:1883-1886` `validateCurve` 只校验 `length >= 4 && length % 2 === 0 && 全部有限`，**未按 timeline 维度区分**，故 translate 传 4 元 curve 会通过审查。
缓解因素：项目规则「Agent 凭空生成新动画时默认不写 curve」，实际路径已规避；风险点在于 `spine_set_bone_keyframe` / `spine_apply_pose_keyframes` / `spine_apply_pose_sequence` 的 `curve` 参数允许 Agent 自由传值。

### 4. 建议（待用户确认后实施，改前须同步 docs/官方JSON规范审查.md）

`validateCurve` 增加维度规则：rotate → 4 元；translate/scale/shear → 8 元；不足则报 error 而非放行。

## 单臂透视缩放：两个疑问的代码核查（用户提出，仅审查未改码）

### 疑问一：会不会影响正常缩放 / 骨骼 / IK 关系

核查依据 `src/perspective.ts`：

| 对象 | 实际影响 | 代码位置 |
|---|---|---|
| setup pose / 骨骼 length / 结构 / 皮肤 / mesh | **不改**，只改 runtime 实例 `scaleX/scaleY`，写入落在 `bones.scale` 时间线（相对 setup 相乘） | :49、:104-107 |
| 现有 IK / transform / path 约束 | **不共存，直接 throw 拒绝**（不优雅降级） | :45-46（diagnostic）、:96（calibrated） |
| 镜像 / shear / 奇异父变换 | 拒绝；要求 shearX/Y=0、scaleX/Y>0、transformMode 白名单（上臂 normal/noRotationOrReflection，下段与手必须 normal），祖先 det>1e-10 | :43、:48、:94、:97 |
| 放大 / 翻转 | 禁止，`upper/lower ∈ (0,1]`「不开放翻转或放大」 | :21 |
| 手骨骼 c 的**下游子节点**（手指/持握物） | **会跟着缩，未补偿**——补偿只到链内 c | :107 仅 `c.scaleX *= endNorm[0]/|..|` |
| 非等比缩放（widthUpper/lower 独立，(0,2]） | 允许，会在子节点世界空间产生 shear 效应；官方 runtime 对非等比父缩放的 IK 本有限制 | :66 注释自认「非均匀父变换下解析下段角只能作近似」 |
| 其它动画 | 不受影响（只改目标动画） | 写入层既定行为 |

### 疑问二：内部计算公式是否稳定可控

**结论：不是闭式公式，是迭代近似；确定性有、收敛性没有。**

- 求解器 `src/poseRefinementMath.ts` 的 `boundedLeastSquares`：LM 风格，数值雅可比（有限差分）+ 带主元消去 + 阻尼重试（lambda 1e-8~1e8）+ 回溯线搜索（step 1→1/128）+ 上限 60 次。
- **确定性 OK**：无随机数、固定步长差分、固定主元规则 → 同输入同输出，可复现。
- **收敛性无保证**：`reason` 可能 `localStall`（阻尼爆掉）或 `iterationLimit`（60 次用完）。历史记录里 0.8/0.7 就是 33 次局部停滞、手目标误差 4.39 未通过。
- **当前没失控靠的是四道外部闸门，不是公式本身**：①范围收窄到 0.85–1；②逐样本真实 player 截图 + `assertCaptureReadback`；③33 帧连续性诊断（numericOk + branchStable + 每帧 runtimeHash）；④五项独立人工审查理由 + 批准绑定校准字节哈希。

**关键发现（候选根因，待实测）**：`perspective.ts:112` `initial=[a.rotation, offset+bend*60, input.upper, input.lower]` 把「请求的世界比例」直接当作「局部 scale 初值」，而 `:85` 注释明确写「局部 scale 是待解变量，不能当作请求的缩短比」——**初值语义自相矛盾**，很可能是强缩短局部停滞的原因之一。另 `:114` 的 `try{...}catch{}` 静默吞掉 `worldAngle` 失败，使初值策略在不同输入下不一致。

### 实测：局部 scale 与世界段长的关系（xiaoren.json，链 root→juese→juese-2）

- **等比（scaleX=scaleY=s）**：前臂世界比与手尺度比 **精确等于 s**（0.9/0.85/0.8/0.7 偏差 0）→ **可闭式反解**。
- **非等比（只缩 scaleX，scaleY=1）**：前臂世界比 = 0.99878 / 0.99822 / 0.99768（对应 s=0.9/0.85/0.8），**既不线性也不等于 s**（段长是向量模，取决于段方向 x/y 分量占比）→ **不可闭式**，且 θ 本身也是待求量，耦合。

→ 稳定化方向：等比 + normal 继承走闭式反解（可作解析种子并单测）；非等比保留迭代但初值改用闭式估计、去除静默 catch、输出迭代轨迹与单调性检查。

## 点状骨骼位移透视方案（用户提出工业做法，已产出方案文档）

用户提出真人 2D 骨骼动画的标准做法：**大臂末端挂点状子骨骼 P1，小臂绑定 P1 下；小臂末端挂 P2，手掌绑定 P2 下；mesh 同时绑定每段骨骼与其末端点状骨骼做平滑权重过渡；用点状骨骼的位移（而非缩放）制造空间透视**。规律：垂直于画面的部件变短、平行于画面的变长，且透视边长不超过原长。

**这个方案正好消掉上面两个缺口**：位移不传递缩放 → 不污染子骨骼；IK 用 `bone.length` 不读 scale → 可共存；且有闭式公式。

- 公式：`L′ = L·cos θ`（θ 为肢体轴与画面平面夹角），`Δ = L(1−cos θ)` 沿轴指向根部。`cos θ ≤ 1` 天然满足"不超过原长"。
- 数值表（已用 node 核算）：0°→1.0000/0；15°→0.9659/0.0341；30°→0.8660/0.1340；45°→0.7071/0.2929；60°→0.5/0.5；75°→0.2588/0.7412；90°→0/1。
- **θ 必须由创作意图显式给出，不自动推断**（沿用项目"不声称恢复真实深度"原则）。
- 坐标约定：位移施加在**父骨骼局部系**，沿该骨骼长度轴指向根部；Spine 多为局部 +x **但不保证**，实施前必须读取 setup 确认，不得硬编码。

**关键决策：不突破 V1 边界。** `AGENTS.md:26` 禁止改 bones/skins/mesh，所以 MCP **不自建点状骨骼、不刷 mesh 权重**；改为「资产前置条件 + 只读校验 + 只写 translate 关键帧」。只写 translate 落在现有 V1 白名单内，`spine_set_bone_keyframe` 现成可用。

与现有 scale 方案关系：**并存 + 严格互斥**（同肢体同帧不得同时声明两种透视）；不废弃 npc1 0.85–1 的既有批准与证据。

**实测样本不满足**：`xiaoren.json` 皮肤附件类型**只有 region，无 mesh** → 缺权重过渡，位移只会让部件整体平移导致重叠/断裂。需另找满足条件的真实角色。

**产出**：`docs/点状骨骼位移透视方案.md`（状态标注"未实施"）。含背景三缺口、机制、对比表、公式与坐标约定、资产前置条件 6 项清单、与 scale 方案关系、边界决策、5 项未解决风险、8 步实施建议。

**未解决**：IK 共存时的目标同步策略；多段同时透视须从根到末端依次应用；θ 到实际视觉长度的映射在有斜视角/正交相机时需另行校准；尚无真实资产验证。

## 点状骨骼是否需要特殊命名（用户提问，已落文档 §4.1）

**结论：不强制命名，三层机制，只有 L1 显式声明有授权效力。**

- **L1 显式声明（授权）**：mapping 新增 `perspectivePoints.{leftArm,rightArm}.{upper,lower}`，经既有 `spine_confirm_mapping` 确认后生效。与项目"确认结果是真实写入门禁"原则一致。
- **L2 命名约定（仅候选提示，不授权）**：建议格式 `<段名>_depth`（如 `upperArm_depth`），供人工制资产时参照，命中则给候选减少确认成本。
- **L3 结构机检（仅校验/反查）**：`length=0` + 是目标骨骼子级 + mesh 权重受其影响。

**不给命名授权的三条理由**：① 强制命名等于要求所有既有美术资产返工；② Spine 生态无此惯例（helper/IK target/自定义名各异）；③ 同名或"名字像控制点实为武器挂点"会静默产生错误位移——正是本文档要防的那类静默错误。项目先例：`AGENTS.md`「骨骼原点只作候选，需切片依据才能确认视觉关节」= 不接受自动确认。

**真正解法是语义映射不是命名**：大模型引用 mapping 语义键（`perspectivePoints.leftArm.upper`）而非骨骼全名（如 `bone3`），沿用现有 mapping 模式（Agent 本就用 `leftArm` 而非 `["bone3","bone4","10"]`）。

**与现有 `bones.leftArm` 保持独立、不合并**：现有链是 3 段真实骨骼，`perspective.ts:41` 依赖 `chain.length === 3`，并入会破坏既有 scale 方案与映射语义。

**新增校验项（本轮发现）**：声明时需记录该点状骨骼是否**专用**。若同时承担 IK target / 武器挂点 / 附件绑定，位移会有连带副作用，应拒绝或要求显式声明已评估。

已写入 `docs/点状骨骼位移透视方案.md` §4.1。工作树现有 3 项未提交改动（新增方案文档、项目进展、memory）。

## 质疑「大模型真能精准找到这些特殊处理吗」（成立，且暴露硬缺口）

用户追问：整套方案要对骨骼/骨骼组做特殊处理，大模型真能精准找到？**质疑成立，我上一轮的"语义映射就够了"不完整。**

**区分两件事**：
- **发现阶段**（从角色里找出透视控制点）→ 大模型**不可靠**。命名、`length=0` 都只是启发式，模型可能自信地选错骨骼。
- **使用阶段**（结构已可靠声明后施加位移）→ 可以，写入本身是确定的。
- 真正的风险：语义键 `perspectivePoints.leftArm.upper` 给模型**虚假的确定感**——看到字段存在就以为结构成立。声明错了后面全静默地错。

**实测硬缺口（已核实，非推测）**：
```
含 mesh / weight / vertex 的 MCP 工具：无
spine_get_skins 返回：仅 {skinCount, slotCount, attachmentCount}，无权重
skeleton-4.1.json 附件字段：x, y, rotation, width, height（region，无 vertices）
```
→ **当前 MCP 无法查询"哪个 mesh 顶点受哪些骨骼影响、权重多少"**。后果：§4.1 的 L1 显式声明**缺少客观校验**，退化成人工口头保证。

**已修正文档错误**：§4 条件 3「mesh 权重」的「可否机检」原标"可"**是错的**，已改为"否（当前无查询能力，见§4.2）"。

**设计原则（写入 §4.2）**：不让模型凭空找，而是「**系统枚举事实 → 模型做选择题 → 客观校验拥有判定权**」。四环节：枚举候选（需新增只读能力）→ 静态反验（length≈0/子级/权重）→ **行为反验**（施加小位移后 runtime 回读 mesh 顶点实际位移，确认随权重平滑移动而非硬切）→ 视觉确认（沿用既有门禁）。

**行为反验最强**：不依赖任何命名或静态假设，直接观测"移动这根骨骼那片网格动不动、怎么动"，是把判定权从模型主观判断拿回来的关键。

**结论**：单靠大模型不能可靠完成；补齐「mesh 权重查询」+「试算回读」两项只读能力后才可行，否则校验链是断的，**不应进入实现**。这比 §7.5 的"真实资产"又多一道前置门槛。

## 【重大】透视结构与现有三段链映射模型直接冲突

用户追问：为透视而插入点状骨骼后，手臂不再是 [上臂、小臂、手掌] 而是 [上臂、上臂点、小臂、小臂点、手]，大模型和 MCP 如何完成映射？**查证结果为硬冲突，非配置问题。**

**代码证据（5 处硬依赖）**：
- `motionEngine.ts:89-91`：`chain[i].parent` 必须 === `chain[i-1]`，否则抛「不是连续骨骼链」→ 填 `[大臂,小臂,手]` 时小臂 parent 是 P1 ≠ 大臂 → **非法**
- `mappingTools.ts:50` / `perspective.ts:41` / `retargetEngine.ts:140`：`chain.length !== 3` 抛错 → 填 5 段也**非法**
- `hostPosePatch.ts:69`：`chain?.length === 3 && chain[2] === anchor?.bone`

→ 现有 mapping 连 `spine_calibrate_mapping` 都过不去，confirm / retarget / motion 提取 / pose patch **全部失效**。

**根因（重要认知）**：不是 Spine 限制（`大臂→P1→小臂` 是合法层级），而是**项目映射模型表达力不足**。Spine 里「层级链」与「权重域」本是同一棵树；点状骨骼的角色是**跨域共享控制点**——必须同时属于上一段的权重域（让大臂 mesh 收缩）和下一段的层级链（带动小臂平移）。现有三段连续链假设只能表达一端。

**解法选项**：A 旁支（无效，P1 不带动小臂）/ B transform constraint（V1 禁写区且 `perspective.ts:45` 拒绝被约束接管的链）/ C 改造链模型（要动 5 处，影响 retarget·motion·pose·host 全链路，回归面大）/ **D 新增平行结构（推荐）**：保留现有三段链零改动，透视角色另走 `leftArm:{segments, depthPoints}`，两套并存按类型判别。

**建议**：采用 D，并明确登记为**架构级变更而非增量功能**。在 D 落地前本方案**不具备实施条件**，状态应为「设计冲突已识别，待决策是否立项」而非「待实现」。需产品优先级判断：为透视引入一套平行映射结构是否值得；若否，应归档。

已写入 `docs/点状骨骼位移透视方案.md` §9。

## 解法：段与透视点打包映射 + 资产方命名标准（用户提出，已验证可行）

用户提出：把「上臂 + 上臂点骨骼」**打包映射**，并愿为点骨骼定制命名标准（段 `arm1` → 点 `arm1-toushipoint`）。**这解开了 §9 的死结，冲突从架构级降级为一处校验调整。**

**关键设计：平铺映射表，不改现有链（向后兼容）**：
```json
"bones": { "leftArm": ["arm1","arm2","hand"] },        // 保持 3 段不变
"depthPoints": { "arm1": "arm1-toushipoint", "arm2": "arm2-toushipoint" }
```
→ 5 处硬依赖里 **4 处不受影响**（3 处 `chain.length===3` + `chain[2]===anchor.bone`），**只需改 1 处**。

**连续性校验最小改法**（`motionEngine.ts:89-91`）：
```
parent === chain[i-1]  →  parent === chain[i-1] || parent === depthPoints[chain[i-1]]
```
附加约束：一段最多一个透视点；透视点必须是该段直接子级；透视点不得再声明自己的透视点。

**命名标准已实测验证**：反向以后缀为锚从末尾剥离，**确定性成立**——即使段名本身含 `-`：`foo-bar-toushipoint`→`foo-bar` ✓、`juese-2-toushipoint`→`juese-2` ✓（样本骨骼确实大量含 `-`，如 `juese-2`）。

**命名三原则**：① 后缀在资产内唯一用途，避免 `-end`/`-tip`/`-末端` 等美术可能已用的词（`toushipoint` 满足）；② 段骨骼名本身不得以该后缀结尾（需显式校验）；③ 大小写规则统一。

**重要边界**：命名标准只解决"发现效率"，**不解决"是否正确"**——名字对了但 mesh 权重没刷，透视依然无效。§4.2 的行为反验（位移后 runtime 回读顶点）**不可省略**。

**§9.5 结论已修订**：平铺表使选项 D 成本大幅下降，不必新建平行结构；但 §7.5 真实资产与 §4.2 权重查询两项前置**仍在**。

已写入 `docs/点状骨骼位移透视方案.md` §9.6。
