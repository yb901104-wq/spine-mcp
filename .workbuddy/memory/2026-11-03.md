## 官方 JSON 文档对照与 curve 维数缺陷（重大发现）

用户提供 [Spine JSON 格式文档](https://zh.esotericsoftware.com/spine-json-format) 作为参考。用户判断：一份文档无法覆盖所有版本，版本间细节差异正常。**该判断成立，已实测确认。**

### 1. 该中文文档是 3.8 口径，与 4.1.24 有硬冲突（项目实现均正确，未盲信文档）

| 项 | 官方中文文档 | 4.1.24 runtime 实际 | 项目 |
|---|---|---|---|
| rotate 关键帧字段 | `angle` | `value`（SkeletonJson.js:972 `getValue(keyMap,"value",…)`；:623 rotate→readTimeline1） | ✅ 用 value |
| 绘制顺序 timeline 名 | `draworder`（全小写） | `map.drawOrder`（:892） | ✅ 用驼峰 |
| curve X 轴单位 | 「单位是帧」 | cx 为 0..1 归一化（readCurve 里 cx 不乘 scale，cy 才乘） | — |

结论：官方文档只能作**字段语义参考**，不能作**写入校验依据**；真正依据是 4.1 runtime 源码 + 当前版本真实样本。项目 `docs/官方JSON规范审查.md` 里「官方文档字段含义 + 4.1.24 样本字段形态双重规则，差异必须记录」的策略是对的。

### 2. 真正的缺陷：curve 在二维 timeline 上必须是 8 元，官方文档完全没写

- runtime `readCurve(curve, …)` 内 `let i = value << 2;` —— `value` 是**维度索引**，二维 timeline 第二维度从 `curve[4]` 起取。
- 实测样本 `xiaoren.json`：rotate 的 curve 恒为 **4 元**，translate/scale/shear 恒为 **8 元**（前 4 给 x、后 4 给 y）。
- 实测后果（bone2 translate，6 个 8 元 curve 截成 4 元）：**41 帧中 40 帧 y 值为 NaN，x 值完全正常、无任何报错**。属静默污染，x 分量正常极具迷惑性。

### 3. 项目侧缺口

`src/spineJson.ts:1883-1886` `validateCurve` 只校验 `length >= 4 && length % 2 === 0 && 全部有限`，**未按 timeline 维度区分**，故 translate 传 4 元 curve 会通过审查。
缓解因素：项目规则「Agent 凭空生成新动画时默认不写 curve」，实际路径已规避；风险点在于 `spine_set_bone_keyframe` / `spine_apply_pose_keyframes` / `spine_apply_pose_sequence` 的 `curve` 参数允许 Agent 自由传值。

### 4. 建议（待用户确认后实施，改前须同步 docs/官方JSON规范审查.md）

`validateCurve` 增加维度规则：rotate → 4 元；translate/scale/shear → 8 元；不足则报 error 而非放行。

## 单臂透视缩放：两个疑问的代码核查（用户提出，仅审查未改码）

### 疑问一：会不会影响正常缩放 / 骨骼 / IK 关系

核查依据 `src/perspective.ts`：

| 对象 | 实际影响 | 代码位置 |
|---|---|---|
| setup pose / 骨骼 length / 结构 / 皮肤 / mesh | **不改**，只改 runtime 实例 `scaleX/scaleY`，写入落在 `bones.scale` 时间线（相对 setup 相乘） | :49、:104-107 |
| 现有 IK / transform / path 约束 | **不共存，直接 throw 拒绝**（不优雅降级） | :45-46（diagnostic）、:96（calibrated） |
| 镜像 / shear / 奇异父变换 | 拒绝；要求 shearX/Y=0、scaleX/Y>0、transformMode 白名单（上臂 normal/noRotationOrReflection，下段与手必须 normal），祖先 det>1e-10 | :43、:48、:94、:97 |
| 放大 / 翻转 | 禁止，`upper/lower ∈ (0,1]`「不开放翻转或放大」 | :21 |
| 手骨骼 c 的**下游子节点**（手指/持握物） | **会跟着缩，未补偿**——补偿只到链内 c | :107 仅 `c.scaleX *= endNorm[0]/|..|` |
| 非等比缩放（widthUpper/lower 独立，(0,2]） | 允许，会在子节点世界空间产生 shear 效应；官方 runtime 对非等比父缩放的 IK 本有限制 | :66 注释自认「非均匀父变换下解析下段角只能作近似」 |
| 其它动画 | 不受影响（只改目标动画） | 写入层既定行为 |

### 疑问二：内部计算公式是否稳定可控

**结论：不是闭式公式，是迭代近似；确定性有、收敛性没有。**

- 求解器 `src/poseRefinementMath.ts` 的 `boundedLeastSquares`：LM 风格，数值雅可比（有限差分）+ 带主元消去 + 阻尼重试（lambda 1e-8~1e8）+ 回溯线搜索（step 1→1/128）+ 上限 60 次。
- **确定性 OK**：无随机数、固定步长差分、固定主元规则 → 同输入同输出，可复现。
- **收敛性无保证**：`reason` 可能 `localStall`（阻尼爆掉）或 `iterationLimit`（60 次用完）。历史记录里 0.8/0.7 就是 33 次局部停滞、手目标误差 4.39 未通过。
- **当前没失控靠的是四道外部闸门，不是公式本身**：①范围收窄到 0.85–1；②逐样本真实 player 截图 + `assertCaptureReadback`；③33 帧连续性诊断（numericOk + branchStable + 每帧 runtimeHash）；④五项独立人工审查理由 + 批准绑定校准字节哈希。

**关键发现（候选根因，待实测）**：`perspective.ts:112` `initial=[a.rotation, offset+bend*60, input.upper, input.lower]` 把「请求的世界比例」直接当作「局部 scale 初值」，而 `:85` 注释明确写「局部 scale 是待解变量，不能当作请求的缩短比」——**初值语义自相矛盾**，很可能是强缩短局部停滞的原因之一。另 `:114` 的 `try{...}catch{}` 静默吞掉 `worldAngle` 失败，使初值策略在不同输入下不一致。

### 实测：局部 scale 与世界段长的关系（xiaoren.json，链 root→juese→juese-2）

- **等比（scaleX=scaleY=s）**：前臂世界比与手尺度比 **精确等于 s**（0.9/0.85/0.8/0.7 偏差 0）→ **可闭式反解**。
- **非等比（只缩 scaleX，scaleY=1）**：前臂世界比 = 0.99878 / 0.99822 / 0.99768（对应 s=0.9/0.85/0.8），**既不线性也不等于 s**（段长是向量模，取决于段方向 x/y 分量占比）→ **不可闭式**，且 θ 本身也是待求量，耦合。

→ 稳定化方向：等比 + normal 继承走闭式反解（可作解析种子并单测）；非等比保留迭代但初值改用闭式估计、去除静默 catch、输出迭代轨迹与单调性检查。

## 点状骨骼位移透视方案（用户提出工业做法，已产出方案文档）

用户提出真人 2D 骨骼动画的标准做法：**大臂末端挂点状子骨骼 P1，小臂绑定 P1 下；小臂末端挂 P2，手掌绑定 P2 下；mesh 同时绑定每段骨骼与其末端点状骨骼做平滑权重过渡；用点状骨骼的位移（而非缩放）制造空间透视**。规律：垂直于画面的部件变短、平行于画面的变长，且透视边长不超过原长。

**这个方案正好消掉上面两个缺口**：位移不传递缩放 → 不污染子骨骼；IK 用 `bone.length` 不读 scale → 可共存；且有闭式公式。

- 公式：`L′ = L·cos θ`（θ 为肢体轴与画面平面夹角），`Δ = L(1−cos θ)` 沿轴指向根部。`cos θ ≤ 1` 天然满足"不超过原长"。
- 数值表（已用 node 核算）：0°→1.0000/0；15°→0.9659/0.0341；30°→0.8660/0.1340；45°→0.7071/0.2929；60°→0.5/0.5；75°→0.2588/0.7412；90°→0/1。
- **θ 必须由创作意图显式给出，不自动推断**（沿用项目"不声称恢复真实深度"原则）。
- 坐标约定：位移施加在**父骨骼局部系**，沿该骨骼长度轴指向根部；Spine 多为局部 +x **但不保证**，实施前必须读取 setup 确认，不得硬编码。

**关键决策：不突破 V1 边界。** `AGENTS.md:26` 禁止改 bones/skins/mesh，所以 MCP **不自建点状骨骼、不刷 mesh 权重**；改为「资产前置条件 + 只读校验 + 只写 translate 关键帧」。只写 translate 落在现有 V1 白名单内，`spine_set_bone_keyframe` 现成可用。

与现有 scale 方案关系：**并存 + 严格互斥**（同肢体同帧不得同时声明两种透视）；不废弃 npc1 0.85–1 的既有批准与证据。

**实测样本不满足**：`xiaoren.json` 皮肤附件类型**只有 region，无 mesh** → 缺权重过渡，位移只会让部件整体平移导致重叠/断裂。需另找满足条件的真实角色。

**产出**：`docs/点状骨骼位移透视方案.md`（状态标注"未实施"）。含背景三缺口、机制、对比表、公式与坐标约定、资产前置条件 6 项清单、与 scale 方案关系、边界决策、5 项未解决风险、8 步实施建议。

**未解决**：IK 共存时的目标同步策略；多段同时透视须从根到末端依次应用；θ 到实际视觉长度的映射在有斜视角/正交相机时需另行校准；尚无真实资产验证。

## 点状骨骼是否需要特殊命名（用户提问，已落文档 §4.1）

**结论：不强制命名，三层机制，只有 L1 显式声明有授权效力。**

- **L1 显式声明（授权）**：mapping 新增 `perspectivePoints.{leftArm,rightArm}.{upper,lower}`，经既有 `spine_confirm_mapping` 确认后生效。与项目"确认结果是真实写入门禁"原则一致。
- **L2 命名约定（仅候选提示，不授权）**：建议格式 `<段名>_depth`（如 `upperArm_depth`），供人工制资产时参照，命中则给候选减少确认成本。
- **L3 结构机检（仅校验/反查）**：`length=0` + 是目标骨骼子级 + mesh 权重受其影响。

**不给命名授权的三条理由**：① 强制命名等于要求所有既有美术资产返工；② Spine 生态无此惯例（helper/IK target/自定义名各异）；③ 同名或"名字像控制点实为武器挂点"会静默产生错误位移——正是本文档要防的那类静默错误。项目先例：`AGENTS.md`「骨骼原点只作候选，需切片依据才能确认视觉关节」= 不接受自动确认。

**真正解法是语义映射不是命名**：大模型引用 mapping 语义键（`perspectivePoints.leftArm.upper`）而非骨骼全名（如 `bone3`），沿用现有 mapping 模式（Agent 本就用 `leftArm` 而非 `["bone3","bone4","10"]`）。

**与现有 `bones.leftArm` 保持独立、不合并**：现有链是 3 段真实骨骼，`perspective.ts:41` 依赖 `chain.length === 3`，并入会破坏既有 scale 方案与映射语义。

**新增校验项（本轮发现）**：声明时需记录该点状骨骼是否**专用**。若同时承担 IK target / 武器挂点 / 附件绑定，位移会有连带副作用，应拒绝或要求显式声明已评估。

已写入 `docs/点状骨骼位移透视方案.md` §4.1。工作树现有 3 项未提交改动（新增方案文档、项目进展、memory）。

## 质疑「大模型真能精准找到这些特殊处理吗」（成立，且暴露硬缺口）

用户追问：整套方案要对骨骼/骨骼组做特殊处理，大模型真能精准找到？**质疑成立，我上一轮的"语义映射就够了"不完整。**

**区分两件事**：
- **发现阶段**（从角色里找出透视控制点）→ 大模型**不可靠**。命名、`length=0` 都只是启发式，模型可能自信地选错骨骼。
- **使用阶段**（结构已可靠声明后施加位移）→ 可以，写入本身是确定的。
- 真正的风险：语义键 `perspectivePoints.leftArm.upper` 给模型**虚假的确定感**——看到字段存在就以为结构成立。声明错了后面全静默地错。

**实测硬缺口（已核实，非推测）**：
```
含 mesh / weight / vertex 的 MCP 工具：无
spine_get_skins 返回：仅 {skinCount, slotCount, attachmentCount}，无权重
skeleton-4.1.json 附件字段：x, y, rotation, width, height（region，无 vertices）
```
→ **当前 MCP 无法查询"哪个 mesh 顶点受哪些骨骼影响、权重多少"**。后果：§4.1 的 L1 显式声明**缺少客观校验**，退化成人工口头保证。

**已修正文档错误**：§4 条件 3「mesh 权重」的「可否机检」原标"可"**是错的**，已改为"否（当前无查询能力，见§4.2）"。

**设计原则（写入 §4.2）**：不让模型凭空找，而是「**系统枚举事实 → 模型做选择题 → 客观校验拥有判定权**」。四环节：枚举候选（需新增只读能力）→ 静态反验（length≈0/子级/权重）→ **行为反验**（施加小位移后 runtime 回读 mesh 顶点实际位移，确认随权重平滑移动而非硬切）→ 视觉确认（沿用既有门禁）。

**行为反验最强**：不依赖任何命名或静态假设，直接观测"移动这根骨骼那片网格动不动、怎么动"，是把判定权从模型主观判断拿回来的关键。

**结论**：单靠大模型不能可靠完成；补齐「mesh 权重查询」+「试算回读」两项只读能力后才可行，否则校验链是断的，**不应进入实现**。这比 §7.5 的"真实资产"又多一道前置门槛。

## 【重大】透视结构与现有三段链映射模型直接冲突

用户追问：为透视而插入点状骨骼后，手臂不再是 [上臂、小臂、手掌] 而是 [上臂、上臂点、小臂、小臂点、手]，大模型和 MCP 如何完成映射？**查证结果为硬冲突，非配置问题。**

**代码证据（5 处硬依赖）**：
- `motionEngine.ts:89-91`：`chain[i].parent` 必须 === `chain[i-1]`，否则抛「不是连续骨骼链」→ 填 `[大臂,小臂,手]` 时小臂 parent 是 P1 ≠ 大臂 → **非法**
- `mappingTools.ts:50` / `perspective.ts:41` / `retargetEngine.ts:140`：`chain.length !== 3` 抛错 → 填 5 段也**非法**
- `hostPosePatch.ts:69`：`chain?.length === 3 && chain[2] === anchor?.bone`

→ 现有 mapping 连 `spine_calibrate_mapping` 都过不去，confirm / retarget / motion 提取 / pose patch **全部失效**。

**根因（重要认知）**：不是 Spine 限制（`大臂→P1→小臂` 是合法层级），而是**项目映射模型表达力不足**。Spine 里「层级链」与「权重域」本是同一棵树；点状骨骼的角色是**跨域共享控制点**——必须同时属于上一段的权重域（让大臂 mesh 收缩）和下一段的层级链（带动小臂平移）。现有三段连续链假设只能表达一端。

**解法选项**：A 旁支（无效，P1 不带动小臂）/ B transform constraint（V1 禁写区且 `perspective.ts:45` 拒绝被约束接管的链）/ C 改造链模型（要动 5 处，影响 retarget·motion·pose·host 全链路，回归面大）/ **D 新增平行结构（推荐）**：保留现有三段链零改动，透视角色另走 `leftArm:{segments, depthPoints}`，两套并存按类型判别。

**建议**：采用 D，并明确登记为**架构级变更而非增量功能**。在 D 落地前本方案**不具备实施条件**，状态应为「设计冲突已识别，待决策是否立项」而非「待实现」。需产品优先级判断：为透视引入一套平行映射结构是否值得；若否，应归档。

已写入 `docs/点状骨骼位移透视方案.md` §9。

## 解法：段与透视点打包映射 + 资产方命名标准（用户提出，已验证可行）

用户提出：把「上臂 + 上臂点骨骼」**打包映射**，并愿为点骨骼定制命名标准（段 `arm1` → 点 `arm1-toushipoint`）。**这解开了 §9 的死结，冲突从架构级降级为一处校验调整。**

**关键设计：平铺映射表，不改现有链（向后兼容）**：
```json
"bones": { "leftArm": ["arm1","arm2","hand"] },        // 保持 3 段不变
"depthPoints": { "arm1": "arm1-toushipoint", "arm2": "arm2-toushipoint" }
```
→ 5 处硬依赖里 **4 处不受影响**（3 处 `chain.length===3` + `chain[2]===anchor.bone`），**只需改 1 处**。

**连续性校验最小改法**（`motionEngine.ts:89-91`）：
```
parent === chain[i-1]  →  parent === chain[i-1] || parent === depthPoints[chain[i-1]]
```
附加约束：一段最多一个透视点；透视点必须是该段直接子级；透视点不得再声明自己的透视点。

**命名标准已实测验证**：反向以后缀为锚从末尾剥离，**确定性成立**——即使段名本身含 `-`：`foo-bar-toushipoint`→`foo-bar` ✓、`juese-2-toushipoint`→`juese-2` ✓（样本骨骼确实大量含 `-`，如 `juese-2`）。

**命名三原则**：① 后缀在资产内唯一用途，避免 `-end`/`-tip`/`-末端` 等美术可能已用的词（`toushipoint` 满足）；② 段骨骼名本身不得以该后缀结尾（需显式校验）；③ 大小写规则统一。

**重要边界**：命名标准只解决"发现效率"，**不解决"是否正确"**——名字对了但 mesh 权重没刷，透视依然无效。§4.2 的行为反验（位移后 runtime 回读顶点）**不可省略**。

**§9.5 结论已修订**：平铺表使选项 D 成本大幅下降，不必新建平行结构；但 §7.5 真实资产与 §4.2 权重查询两项前置**仍在**。

## 参考动态图如何确定 KEY pose（源码核查 + 外部对标调研）

### 本项目实际做法（`src/referenceTools.ts`，已读源码确认）

**`spine_analyze_reference_gif`**：GIF（gifuct-js）/ 多页栅格（sharp）拆帧 → 统一画布合成逐帧 PNG → 每帧 SHA-256 **像素哈希**去重（`duplicateOf`）→ 记录 delay（缺省 100ms）、累计 time、estimatedPeriod（=文件总时长）、loop（NETSCAPE2.0 或 Agent 指定）、alpha 可见边界。**`phases` 由 Agent 显式标注**（time+phase），`phaseSource: 'Agent 标注' | '未标注'`。warnings 自承："相机运动与角色运动不能仅凭拆帧自动区分"、"estimatedPeriod 需 Agent 确认是否完整循环"。

**`spine_extract_reference_keyframes`**：`unique = frames.filter(f=>f.duplicateOf===null)`，然后 `keys = unique[Math.floor(i*(n-1)/(count-1))]` —— **纯按索引等间隔均匀取样**，count 默认 8（2–32）。**没有任何姿态变化量、运动能量、显著性、曲率计算**。

→ **结论：当前不做关键姿态识别。** 选的是 representative frames（时间轴均匀代表帧），不是动画意义的 key pose（极值/转折/接触/重心转移/overshoot）。语义由 Agent 标注 + 后续视觉审查门禁（`create_reference_pose` / `review_reference_pose` / `upgrade_reference_pose` / `create_pose_sequence` 等）赋予。这是有意保守，符合 AGENTS.md「不凭空生成」原则。

**明显短板**：等间隔会漏掉落在采样间隙的关键姿态（如 walk 的 contact 帧）；隐含"节奏均匀"假设，多数动作不成立。工具名 `extract_reference_keyframes` 有误导性。

### 外部成熟做法（调研所得）

| 类别 | 代表 | 做法 |
|---|---|---|
| 模板生成（同类轻量 MCP） | 项目对标过的 `spine-mcp-server` `generate_animation` | 用 sine/bob 相位模板（idle/walk/run/attack…）直接生成曲线，**绕过识别** |
| 姿态估计 + mocap（工业主流） | QuickMagic / Move.ai / Plask / DeepMotion；开源 `mixamo-llm-mocap`（GVHMR+SMPL-X+Blender MCP）、Media to Pose（Blender 扩展，`mode="KEYFRAMES"`） | 拆帧 → 2D 姿态估计（OpenPose/DWPose/MediaPipe/HRNet）→ 2D→3D lifting / SMPL 参数（GVHMR/WHAM）→ 骨骼拟合 retarget → 导出。得到**逐帧密集姿态数据**后再做关键帧简化 |
| 帧差/光流类通用视频摘要 | 光流、运动能量、聚类 | 找 representative frame，**不保证是动画意义的 key pose** |
| **关键帧选择算法（真正定 key pose）** | **Salient Poses**（Roberts/Lewis/Anjyo/Seo/Seol）、Saliency Diagrams、Maya Simplify Curves、RDP、曲线简化/聚类/矩阵分解、专利 CN109190474A 姿势显著性 | Salient Poses 把选择建模成**全局优化**：帧为图节点，边 i→j 代价 = 线性插值近似该区间时的最大关节偏差（无穷范数），DP 求最优 K 帧；优于 RDP 与 Maya，800 帧约 1.5s 预计算；"Error Cliff" 辅助定 K。姿势显著性法用多尺度显著性局部极大值 + 重建误差自适应定数量 |

### 根因判断

外部能"自动确定 key pose"的方案，几乎都建立在**已有骨骼/关键点轨迹**（mocap 数据或 2D 姿态估计序列）之上，再从曲线里找极值/最小重建误差。**本项目只有像素帧，缺"姿态序列"这一层**——所以差距不是算法选型，是能力缺口。

### 建议（分层，均不改现有门禁）

1. **最该做（零成本）**：把 `extract_reference_keyframes` 口径改清楚——改名为"候选代表帧"或至少在描述/文档里写明**它不是 key pose 识别**，避免 Agent 误以为拿到了关键姿态。
2. **低成本**：用已有逐帧 PNG + 哈希算相邻帧差异/变化量曲线，局部峰值作**候选**提供给 Agent，替代或补充等间隔；仍由 Agent 确认，不自动批准。
3. **高成本（慎）**：引入轻量姿态估计得到关键点轨迹，再用 RDP / 简化版 Salient Poses 找极值帧；会引入模型依赖，且 AGENTS.md 明确"图片坐标不可直接传入目标 IK"，需另行设计。

## 参考动态图 KEY pose 候选方案（用户提出"平均帧截取 + 帧差曲线"综合，已评估并落文档）

用户判断「这部分必须补足，否则没法正确识别节奏和 KEY pose」——**成立**。问「平均帧截取 + 逐帧 PNG 算相邻帧差异/变化量曲线综合进行是否合理」。

**方向对（互补），但直接用有一个必须纠正的概念错误**：
- **帧间差异是「速度」，不是「姿态极值」**。最小实验实证：`x(t)=sin(t)`，帧差最大处 t=3.141 / x≈0（**过渡帧**），帧差最小处 t=1.555 / x=1（**KEY pose**）；姿态极值实际在 t=1.571、4.712。
- 若按"差异峰值"选帧，会系统性选出 inbetween/breakdown 而漏掉真正极值，**比等间隔更糟（带"已优化"假象）**。
- 正确：局部极小（停顿/极值）+ 方向反转（加速度/曲率）是候选；局部极大（高速过渡）明确排除；连续零差 hold 段只取端点、段内全排除。

**其他关键修正**：
1. 像素差必须限定 ROI —— 现有 `bounds` 是**所有帧并集**，过宽；改逐帧 bbox，用两帧 ROI 并集区域算差，避免相机/背景/粒子/压缩抖动误判（项目 warning 已自承"相机运动与角色运动不能仅凭拆帧区分"）。
2. 节奏：对速度曲线做自相关/峰间距估 `estimatedPeriod`，替代"文件总时长"，输出置信度，低置信度明确标不可用。
3. 合并策略：均匀取样作**保底骨架**（约 50% 配额，含首尾）→ 显著候选按评分插入 → 最小时间间隔去重 → 总数仍受 count(2–32) 约束 → 每帧标 `uniform`/`salient` 来源。
4. 门禁不变：产出**一律候选**，phases 仍 Agent 显式标注 + 视觉审查，逐项理由，不自动批准。
5. 口径修正：工具名 `extract_reference_keyframes` 有误导性，应改名"候选代表帧"或描述中写明不是 key pose 识别。

**产出**：`docs/参考动态图关键姿态候选方案.md`（状态：未实施），含现状、概念错误与实测、修正设计 6 小节、验证判据（召回/假阳性/hold 段/周期偏差）、实施边界（纯只读、不引入姿态估计模型、不自动批准）。

**与成熟方案的差距保持诚实**：Salient Poses 等建立在已有骨骼/关键点轨迹上做全局最优重建；本项目只有像素帧，本方案只做「可审计的候选 + 证据」，不做全局最优，也不自动判定。

## 参考动态图 key pose：同行做法核查（含自我修正）

用户反驳：「别的 MCP 同样拿视频/动态图做参考，也一样没有先验骨骼/关键点轨迹，它们怎么划分 key pose？」——**该反驳成立，此前论断有误。**

**修正**：此前说「能自动定 key pose 的成熟方案几乎都建立在**已有**骨骼/关键点轨迹之上」。错在把"我们先没有"说成"别人天生有"。正确表述：**别人是专门用一个 stage 把这一层从视频里造出来的**（pose estimation）。路线取舍依据是**输入域是否匹配**，不是能力是否先验存在。

**核查到的三条路线（依据公开 README 与论文，未本机跑模型）**：
- **A 先造轨迹再数值 beat 检测**：`mixamo-llm-mocap`（GVHMR→SMPL-X→33 landmarks→`analyze_landmarks.py`→action_spec→Blender MCP）。**不做 key pose 划分**，产出的是语义节拍表（support schedule / rest blends / fist states）；信条"beat 决策来自数字，绝不靠肉眼看帧"。硬要求：锁定机位、T-pose 首尾、干净背景、~8GB VRAM。
- **B 交给多模态模型看**：`blender-animation-mcp`（`setup_video_reference` / `render_video_overlay` / `inspect_video_overlay` / `video_frame_offset`）。**不做 key pose 检测**；官方推荐循环明确"在触点附近、极限姿态处、明显不连续处用 render_frame 检查"——触点与极限由**模型视觉判定**。它提供的是**基础设施**：叠加对齐 + 联系表（上限 25 帧）+ 逐帧渲染 + 世界变换采样。定位原话："让多模态模型能看见自己做的动画，而不是只对着 transform 数字推理"。
- **C 纯像素运动分析**：Frontiers 2017（LK 光流→motion energy→局部极值→extent 过滤）、KFSENet（dM/dt 极值）。存在且不需要骨骼，但目标是**动作识别**不是动画 keying。

**两个须记住的技术判断**：
1. **路线 A 对本项目输入域不匹配**：照片训练模型在风格化 2D 图上失效（Meta Animated Drawings 明确记载"trained on photographs perform poorly on children's drawings"，需 fine-tune on amateur sketches）；且 Animated Drawings 本身是把**预设 BVH 重定向到静态画**，绕开了本问题，仓库 2025-09 已归档。本节 A 对像素/二次元素材的失效率**未经实测**，属推断。
2. **extent 过滤对动画有害**：开合跳中张开（extent 大、速度≈0）保留、收拢（extent 小、速度≈0）被滤掉——而收拢/接触/中性极限正是动画必需关键姿态，会**系统性丢掉一半**。故本项目只取速度极小，extent 降级为**输出证据**而非过滤条件。

**定位结论**：同行没有从视频自动划分 key pose 的通用解法。务实组合 = **B 为主（模型视觉判定 + 审查门禁）+ C 为辅（像素运动能量给可审计候选与节奏证据）**，A 待输入域匹配再评估。
本项目已有 B 的骨架，缺两项：①**叠加对齐基础设施**（当前只有并排对比，无 overlay / 时间轴 offset）；②C 的候选提议器（即方案§3）。

已写入 `docs/参考动态图关键姿态候选方案.md` 新增 §6（含 6.1 修正、6.2 三路线表、6.3 A 不适用、6.4 与 C 的分歧、6.5 定位结论），并修正 §5 边界条目指向 §6。

## 关键澄清：MCP 没有视频内容类型，"抽帧"正是省 token 的手段

用户追问：「其他成熟 MCP 直接让大模型用视觉读参考视频，我们还在抽帧，难道抽帧能省很多 token？为什么有前者还选后者？」

**前提需反转（已实测）**：MCP 协议无 video 内容类型。项目依赖的 `@modelcontextprotocol/sdk` 类型定义中 content block 仅 `TextContent` / `ImageContent` / `AudioContent` / `EmbeddedResource`，全文检索 `video` **0 命中**。所以模型消费参考动态素材的唯一途径就是**逐帧当图片送入**——`blender-animation-mcp` 的 `setup_video_reference` 实为把 MP4 加载进 Blender 视口作背景，再由 `render_video_overlay` 合成后以 image content 返回。

**结论**：抽帧不是妥协，**它本身就是省 token 的手段**（成本 ≈ 帧数 × 单帧成本；8 帧 vs 60 帧全喂）。同行差异不在"抽不抽"而在"抽得更聪明"：按需任意帧、overlay 叠加（两张并排压成一张）、时间轴 offset 对齐。

## 架构认知：为什么 3D MCP 的叠图能"调到差不多一致"，我们不能

用户质疑：「成熟 3D MCP 的参考也不会完全一致，他们怎么就能靠叠图调到大概一致？」**这是本项目叠图能力的真正缺口，比"对齐算法准不准"更根本。**

**核实依据**：
- `blender-animation-mcp` 能力清单：可 inspect cameras、sample evaluated world transforms/bboxes、`key_pose_bone`、create_limb_ik + `key_paw_pose`（世界空间）、`render_frame` 任意帧实时渲染、`evaluate_animation` 世界变换数值、`video_frame_offset` 时间对齐、官方推荐循环明确写 "Iterate"。
- 本项目 `animationReview.ts:17`：对齐全靠 `rs=poses.targetScale*poses.standardHeight/view.height`、`refY=h*.9-(groundY-crop[1])*rs`、`refX=w/2-crop[2]*rs/2`，**三个量全来自 poseManifest**。
- `spine_render_animation_comparison` 的 10 个参数白名单（`animationCommands.ts:53`）**没有任何空间对齐入参**，模型无法调 crop/scale/offset。
- `rs` 的源头 `poseWorkflow.ts:216` 的 `sc=height*.7/standardHeight` 是给**姿态对比页**设计的相机，不是给叠加对齐设计的。
- `referencePose.ts:49` 的 crop/groundY/height 由 Agent 人工标注、一次固定。

**四条根因**：
1. **共享坐标系与否**：3D 里参考视频贴在视口背景平面，rig 与参考共享同一 3D 世界 + 同一台相机 → "重合"可通过移动 rig 物理达成；我们这里是外挂 PNG 靠 crop/scale/offset 贴到另一套相机(bounds→canvas)的目标画布上。
2. **对齐看什么**：3D 对齐看**关节/骨骼位置**，外观形象不同无所谓；且 pose estimation → retarget 保证参考关节与目标骨骼一一对应、动作语义一致。我们叠的是**整幅外观像素**，形象/服装/道具不同直接表现为"两个不同角色"。
3. **闭环 vs 开环**：3D 的叠图是**制作过程中的实时反馈**（改 pose → render_frame → 看偏差 → 再改，Iterate）；我们的是**离线批处理审查产物**（输入是已渲染完的 target.frames，一次性出 GIF），模型既不能调参数也无法即时看到"调一下会怎样"。
4. **样本前提**：npc1 那次参考是 reddit 像素持杖少女、目标是空手 Q 版 npc1，连动作/道具设定都不同，且中间没有骨架语义对应 → 任何对齐参数都只能做到"脚底 + 大致身高"。**用这个样本验证"能否调到一致"本身就不成立**，它只适合验证技术实现。

**结论**：缺的不是更准的对齐公式，是**把叠图从审查产物变成制作闭环**。短期可做：把 crop/scale/offset 暴露为 `spine_render_animation_comparison` 可调入参 + 用 `times` 单帧快速重出 + 回读 bbox 数值反馈；中期需把叠图前移到"改 pose 后即时出图"；根本前提是参考与目标共享骨架语义（pose estimation + retarget 链路，对像素素材未打通）。即使全做到，骨架语义不对应时也只能"大致重合"，不得宣称像素级一致。

## 修正：上一条架构认知有误——项目其实有完整的结构骨骼层

用户反驳「可是我们也有通过关节节点制作的所谓结构骨骼啊？」**成立，我上一条的「我们叠的是整幅外观像素」「中间没有骨架语义对应」是错的**，那只是描述 `renderAnimationComparison` 单条链路的实现，不是项目能力上限。已核实：

**项目实际具备（硬证据）**：
- 参考侧：`referencePose.ts:11` 定义 15 个关节 role（head/face/body + 左右肩肘腕 + 左右髋膝踝）；实测 npc1 `pose-comparison.json` 的 `reference.points` 有 **14 个带 x/y/visibility/estimated/confidence/basis 的关节点**。
- 目标侧：`visualRig.ts` 的 `nodes`（boneLocal / meshTriangle）、`segments`、`edges`，`runtimeGraph()` 产出目标骨架。
- 对应关系：`correspondence`（left/right 显式声明），不是靠外观。
- 数值对比：`poseGraph.ts:67 compareGraphs()` 归一化后算结构指标（躯干方向、肩线、髋线、肢体长度、角度…），带 tolerance 与 pass/fail/unverifiable。
- **迭代求解器**：`referencePoseRefinement.ts` 的 `graphResiduals()` + `boundedLeastSquaresTask(iterations:60)` 的 `refineReferencePose()` —— **这就是 3D「调到一致」在本项目的对应物**，用骨架残差迭代优化姿态。
- 绘制：`referencePose.ts:57 drawReferenceSkeleton()` + `visualRig.ts:44 drawVisualGraph()` 已存在，`poseWorkflow.ts:224/228` 在诊断图上画了两侧骨架。

**因此缺口的精确定位（替代上一条的四条根因）**：
1. 骨架层**只在姿态级**生效（`renderPoseComparison` / `refineReferencePose`），且诊断图是**上下排列**（参考骨架在上半幅、目标骨架在下半幅），不是叠加。
2. `renderAnimationComparison`（动画级、逐帧、本次新增可叠加）**完全没引用骨架层**，只 `drawImage` 整幅外观 → 这才是 npc1 叠图看到「两个不同角色」的原因。
3. 骨架残差的「改 → 看偏差 → 再改」闭环在**姿态生成阶段就结束**，动画级回放时不再迭代。
4. 所以「3D 能调到一致」的能力本项目**大部分已有**，只是**没贯通到动画级叠图**；不需要新建 pose estimation + retarget 链路（上一条这条建议作废）。

**实施方向的修正**：上一轮建议「先把 crop/scale/offset 暴露成可调入参」应降为次要。真正该做的是**给 overlay 增加 skeleton 模式**：复用已有 `drawReferenceSkeleton` + `drawVisualGraph` 把两侧骨架叠在同一画布，并显示 `compareGraphs` 的 metrics/residuals。这样模型看的是关节偏差而非外观差异，形象/服装/道具不同便不再是障碍。

1. `target.trajectories` 是 **108 帧逐帧**，每帧 `bones` 有 53 根骨骼 worldX/worldY；但 `semantic` **全空 0/108**（因该次渲染未传 mappingPath，见 `previewRenderTools.ts:79-85` 的 `if(mapping)` 分支）。→ 目标侧需 visualRigPath 做「骨骼名→语义 role」静态映射，缺省则降级并标注 semanticMapped:false。
2. **参考侧 `poses.reference` 是单帧静态标注**（`time=0`、`imagePath=frame-0000.png`、14 个点 + 8 条 edges，无逐帧关节点）。→ 本方案等价于 3D MCP 的 `render_video_overlay` **for exact key poses**，**不是逐帧骨架追踪**；报告必须显式标注 single-frame，不得宣称逐帧对齐。
3. **两套 rs 不一致（最大实施风险）**：`animationReview.ts:17` 用 `rs=poses.targetScale*poses.standardHeight/view.height`；`poseWorkflow.ts:216` 用 `sc=height*.7/standardHeight`、`:224` 用 `rs=height*.7/r.height`。骨架叠加若直接复用姿态级 rs 会假性错位 → 计划要求 Step 3 投影先行 + 数值断言。
4. `correspondence` **不在** `pose-comparison.json` 的 `poses[]` 里（实测该数组只有 posePath/id/time/stageId/referenceTime/fingerprint）→ ② metrics 取不到时输出 null + 原因，不编造。
5. `pose-comparison.json` 的 `reference` 键：imagePath/time/facing/crop/height/groundY/basis/points/support/grip/edges（**无 silhouette**）。
6. 真实资产验证素材：`目标/npc1.json` 需补复制（当前隔离副本缺）；`trial/npc1.visual-rig.json` 存在于 `/d/AI_cc/spine test/body-reference-trials/2026-10-24T15-53-20-542Z/creation-completion-trials/.../trial/`，实施前须核对 sourceFingerprint 是否匹配，不匹配则拒绝语义映射并降级。
7. `spine_render_pose_comparison` 白名单（animationCommands.ts:50）已有 posePaths/stageIds/targetTimes/outputDir/width/height/region；其 `e.comparison` 来自 `comparePoseGraphs`（poseWorkflow.ts:211）。骨架层在姿态级完整可用，动画级缺的是贯通。
