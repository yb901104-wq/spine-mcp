## 更正：S 依赖的不是「宿主」，是「官方命令行批处理」（1.5 节已补入对比文档）

- 用户质疑「Spine 不是闭源商业软件吗，它怎么当宿主的」——质疑成立，**前稿「编辑器在环的宿主」用词不准**。
- 事实核查（依据官方 <https://en.esotericsoftware.com/spine-command-line-interface>）：
  - Spine 虽闭源，但**官方文档公开提供 CLI**，属官方正门，非破解/逆向/注入。
  - Windows 安装包自带两个可执行文件：`Spine.exe`（GUI，不等待退出）与 **`Spine.com`**（CLI，输出重定向到 console **且阻塞等待退出**）。官方明确推荐 COM 版做命令行调用——S 的 `constants.ts:9` 写死 `SPINE_EXE_NAME = "Spine.com"` 正对应此条。
  - **官方原话**：「Spine starts, does one or more exports or texture packings, then **exits**」→ **跑完就退出，不是常驻宿主**。`src/spine/cli-executor.ts:48` 就是那行 spawn。所以它是**批处理编译器**（类比 ffmpeg/gcc），不是宿主。
  - S 用的参数与官方示例逐字一致：`-i -o -r`（import-service.ts:62 vs 官方 `Spine -i /path/to/skeleton.json -o /path/to/project.spine -r skeletonName`）、`-i`（Info 取版本，version-validator.ts:80）。
- **更底层的分野应是「集成面」**（你站在程序的哪个位置跟它说话），三分而非按真值分：
  - A 进程外·批处理 CLI（S）：argv + stdout 文本 + 退出码 + 磁盘产物；**无会话**（进程每次都退出）
  - B 进程内·常驻插件 + Socket（Blender/Unity）：直触内存活对象；宿主进程天然就是会话
  - C 无宿主·自带引擎（我们）：同进程 import spine-runtime；自建 activeDoc/journal/undo
- 这条更正**反过来解释了前稿两个疑点**：S 全仓 grep 不到 dryRun/expectedHash/审查令牌/写者锁/journal/undo，且是五方中唯一无会话——因为批处理进程没有内存中可串行化的东西，跨调用唯一存活的是磁盘文件，保护只能到 `.bak` + rollback。它的广度（70 工具跨 7 域）是用**放弃纵向状态**换来的。
- **我们没走这条路的硬理由**：必须 Pro 授权 $379（Essential $69 官方明确不导入 mesh 与约束、不能保存含 IK 的项目）；许可证限制单一具名用户且「同一时间只有一台在用」，CI 并发会撞；锁死 3.8.75；headless 有例外（官方：导出图片/视频需 OS 窗口系统 + OpenGL，故其 render_preview/export_video 在无图形环境不成立）；拿到的是屏幕文本而非结构化数据（version-validator.ts:39 用正则刮版本号，出错只有 stderr 前 500 字符）；单次调用秒级（启 JVM，其 `-Xmx2048m` 是 JVM 参数），故须 60s 超时保护。
- **反向洞察（重要，影响后续决策）**：我们与 S 正好互补——S 有「编辑器权威」但无会话，我们有会话但无编辑器权威。因此 `docs/plans/host-evolution.md` 要造的常驻宿主，补的是 S **结构上拿不到**的那一层（会话状态），而不是去复刻它的编辑器权威。两条路线不是竞争关系。

## 更正2：官方 CLI **不提供任何动画编辑命令**（1.6 节已补入对比文档）

- 用户后段假设「他们能用官方渠道执行动画命令，我们却要自己编译 JSON 规则手动包 MCP」——**假设不成立，铁证推翻**。
- 对 `src/spine/` 全量 grep 实际传入的 CLI 参数：**只有六个** `-e -i -l -m -o -r`（export / input / logout / clean / output / import），全是**文件级**操作。官方 CLI 参数表里不存在「设骨骼旋转/加关键帧/改插槽/建动画」这类命令。
- 真实链路（`modify-service.ts:29`）：`modifyProject(projectPath, modifyFn: (json:any)=>void, ...)`，注释原文「接收解析后的 JSON 对象，直接原地修改」。`json-handler.ts` 开篇注释是**手写的** animate timeline 结构表（`animations.<name>.bones.<bone>.rotate[] 每帧 {time, angle}` 等），与我们维护的结构知识是同一种东西。
- **量化结论**：按是否依赖 `cliExecutor` 给 `src/spine/*.ts`（30 个文件）分类——**纯 JSON 操作 24 文件 / 4831 行 ≈ 89%**；调 CLI 6 文件 / 577 行 ≈ 11%（还含 cli-executor 封装层自身）。大头：json-handler 1234 行 44 函数、render-service 533、animation-generate 307、assemble 216、split-atlas 213、cut-parts 172、effect 181。
- **S 的 70 个工具不是官方命令的薄包装，绝大多数也是手撸 JSON 变换。** 我们没有因为绕路而多做功。
- **真正的差距只有一条：写完的 JSON 由谁判定格式合规。** S 外包给官方 Spine 导入器（付费 $379 + 锁 3.8.75 + 秒级 + 无会话）；我们自己实现裁判（`docs/官方JSON规范审查.md` 的规范审查层 + 官方 runtime 回读）。AGENTS.md 里「官方 JSON 规范审查必须覆盖 Spine 导入器敏感规则（curve 只描述当前到下一帧、timeline 末帧不能含 curve）」**就是人工复刻 S 白嫖到的那个裁判**。
- 由此的建议（已在 §1.6.5 落盘）：**接 CLI 可以，但只做默认关闭的 advisory 终验**，仅回答「这文件 Spine 编辑器能否打开」，不进主链路、不放宽任何门禁。

## 经验

- 新能力挂载后若全量回退，先怀疑**新测试自身污染**（env/注册表/全局 profiles），再怀疑产品代码。
- 跑测试前后必查 `.spine-mcp/writer.lock` 与 `.spine-mcp/locks/`；回收前先用 PowerShell 确认 PID 已不存在，再走 `recoverDeadWriter`。
- 本环境下 `npm test` 全量跑会触碰 safe-delete 批量删除拦截阈值；分批按文件跑可绕开，用于区分「环境拦截」与「真实失败」，但不能当全量结论。
- 跑测试前/后要检查 `.spine-mcp/writer.lock`，残留锁会让大量用例级联失败并被误读为回归。
