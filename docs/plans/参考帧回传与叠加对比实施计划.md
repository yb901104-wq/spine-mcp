> **状态：计划（未实施）。** 2026-11-03 制定。依据 `docs/参考动态图关键姿态候选方案.md` §7.4 与 §8。
> 目标：把"参考素材 → 模型可见 → 与产出对齐对比"这条链路补全，对齐 `blender-animation-mcp` 的 `render_video_overlay` 能力定位。

## 1. 实施项

### ① 参考帧以联系表形式回传图片

**落点**：`src/referenceTools.ts`（及新增内部合成函数）

**设计决策：输出单张联系表，而非 N 张独立图。** 理由三条：
1. `pickImages` 上限 3 张，8 帧直接超限；
2. token 成本——1 张联系表 ≈ 1 张图的成本，N 张 = N 倍；
3. 与项目既有 `renderContactSheet`（`previewRenderTools.ts:109`）做法一致：网格 + 时间标签。

**实现要点**
- 新增内部函数 `buildReferenceContactSheet(frames, dir, columns, maxTiles)`，用 `@napi-rs/canvas`（`referenceTools.ts:3` 已导入）合成网格，每格标注帧序号与时间。
- `extractReferenceKeyframes`：生成 `keyframeSheet` 路径，设 `result.__images = [sheetPath]`。**这是 `__images` 机制的首次启用。**
- `analyzeReferenceGif` / `analyzeRasterReference`：可选产出去重帧联系表（默认取前 12 帧），同样走 `__images`。
- 新增参数：`columns`（1–12，默认 4）、`maxTiles`（默认 12），均带范围校验（沿用项目"入参必须校验"惯例）。

**门禁**：纯只读产物，不触碰 V1 写入边界。不改任何现有字段语义，只新增。

### ② `renderAnimationComparison` 增加 overlay 布局

**落点**：`src/animationReview.ts`、`src/animationCommands.ts`（参数白名单）

- 新增 `layout?: 'reference-above-target' | 'overlay'`，**默认保持 `reference-above-target`**，不破坏既有证据与门禁。
- overlay 分支：`createCanvas(w, h[+标签条])`，先按现有 `rs`/`refX`/`refY` 画参考帧，再以 `ctx.globalAlpha = opacity` 画目标帧（`rasterRenderer.ts:96` 已使用 `globalAlpha`，能力确认可用）。
- 新增 `opacity`（0.1–1，默认 0.6）。
- 输出 `layout: 'overlay'`。

**必须同步修改的门禁**
- `animationReview.ts` 中 `m.layout !== 'reference-above-target'` 的严格相等校验，需改为接受两种布局。
- **约束**：放宽不得削弱"有参考的任务必须提供同步对比"这一要求——overlay 同样必须来自真实渲染、同样绑定 `evidenceFiles`（现有逻辑已含 `gifPath`/各 manifest/参考帧路径，保持）。

### ③ 支持按需取指定帧

**落点**：`src/animationReview.ts`（扩展现有工具，**不新增工具**，保持 116 个不变）

- `spine_render_animation_comparison` 当前按 `target.frames` 全量逐帧。新增 `times?: number[]`，指定时只渲染这些时间点。
- 仍须满足既有 `phaseMap` 严格递增与全覆盖校验（该校验针对 phaseMap 本身，不受 times 影响）。
- 与 ① 的"按需取帧"诉求合并：模型可只取可疑帧，进一步省 token。

## 2. 顺序与依赖

```
① 独立 ──────────────┐
② 独立（依赖现有对齐数学，无需新建）─┼──→ ③（依赖 ② 的 overlay 分支）
```

① 与 ② 可并行；③ 必须在 ② 之后。建议顺序 **① → ② → ③**（① 最小最快，先拿到端到端反馈）。

## 3. 验证方式

| 层级 | 做法 |
|---|---|
| 编译 | `npm run build` |
| 单元测试 | 分文件跑，**不以全量 `npm test` 为准**——全量会稳定失败 25 项，系宿主 `safe-delete` 批量确认守卫（单轮累计删除超阈值 50）触发，与改动无关 |
| 端到端 | MCP stdio 调用，确认返回 `content` 含 `type:'image'` 且 `isError` 为 false |
| 视觉 | 出图人工确认：① 联系表可读（序号+时间清晰）；② **叠加对齐是否正确**（这是唯一无法靠数值断言的部分，必须看图） |

### 3.1 夹具与阻塞点（已查清，勿开工后才发现）

| 项 | 依赖 | 状态 |
|---|---|---|
| ① | 参考 GIF | `example-json/` 下无参考 GIF，**需在测试中合成**（可用 `@napi-rs/canvas` + `GIFEncoder` 生成，项目已有该能力） |
| ② 代码改动 | 无外部依赖 | 可做，用合成 manifest 单测 |
| ② 端到端视觉验证 | `poseManifestPath`（含 `standardHeight`/`targetScale`/`reference.crop`/`height`/`groundY`）+ `referenceManifestPath` | **受既有链路阻塞** |

**② 的阻塞链条（逐层核实）**：
- `poses` manifest 由 `poseWorkflow.ts:241` 产出，字段含 `standardHeight`、`targetScale:sc`、`reference`、`bounds`。
- `poses.reference` 源自 `spine_create_reference_pose`（`referencePose.ts:49`），**要求 Agent 人工标注** `crop`（4 数）、`height`、`groundY`、`facing`、`time`——不是自动推断。
- 而该链路的上游需要 **mapping confirmed + approved pose**，实测当前工作区两者皆无（参见 2026-11-02/03 记录）。

**因此 ② 分两步走**：先做代码改动 + 合成夹具单测（可完成）；**叠加图的视觉正确性验证须待上游链路打通后再补**，不得因为"代码过了单测"就宣称叠加对齐正确——对齐正确性只能靠看图。

另注：`layout:'reference-above-target'` 在**两处**硬编码（`animationReview.ts:23` 与 `poseWorkflow.ts:241`），后者属姿态对比 manifest，本次不改；改动时需确认二者不会互相污染门禁判断。

## 4. 不做的事（范围约束）

- 不新增、删除或重命名任何 MCP 工具（保持 116）。
- 不实现 §3 的运动能量候选提议器（属另一项，另议）。
- 不引入姿态估计模型。
- 不改 `pickImages` 的 3 张上限（既有 token 护栏）。
- 不动 V1 写入边界；三项均为只读渲染与对比。

## 5. 完成判据

- ① 模型调用 `spine_extract_reference_keyframes` 后**无需再自行读文件**即可看到关键帧画面。
- ② 能产出参考帧与产出帧**叠加**的同步图，且可通过既有审查门禁。
- ③ 能只取指定时间点出叠加图，而非必须整段。
