## 1. 施工总原则

### 1.1 先修“会不会误判”，再修“代码是否漂亮”

优先处理会导致以下后果的问题：

- 未确认的 `visualRig` 被当成正式结构依据；
- 结构映射不完整却被当成完整通过；
- 非原点视觉关节被错误当成骨骼原点；
- 普通写入、Host 提交、备份恢复使用不清晰或不一致的安全边界；
- 同一份文件在不同进程中出现不同版本判断。

循环依赖、God Object 和文件拆分属于后续施工，不与功能收口混在同一阶段。

### 1.2 诊断能力与正式验收能力必须分开

当前骨架叠加可以作为诊断工具保留部分映射和降级显示，但正式验收必须有更严格的完整性条件。

- **诊断模式：** 可以显示部分节点、未映射节点和灰色原始轨迹；结果只能说明“当前数据能观察到什么”。
- **正式验收模式：** 必须满足结构资产确认、目标角色匹配、必需视觉节点完整、对应关系完整、指标可计算和证据完整；不满足时只能返回“不可验收”，不能返回“通过”。

### 1.3 结构层、动画层、审查层分别定义数据责任

- **结构层：** `referencePose`、`visualRig`、`correspondence`、骨骼/视觉节点映射。
- **动画层：** `motion`、Spine timeline、预览帧、逐帧轨迹。
- **审查层：** GIF、骨架图、metrics、证据清单、review token。

审查层可以消费前两层，但不能在审查函数内部重新发明一套结构资产审核规则。

### 1.4 所有“通过”必须有可解释的依据

输出中必须区分：

- `mapped`：有节点成功映射；
- `complete`：所有必需节点均已映射；
- `metricsAvailable`：指标可以计算；
- `acceptanceEligible`：满足正式验收条件；
- `approved`：经过人工审查并生成批准令牌。

不能用一个 `semanticMapped: true` 同时表达以上五种含义。

## 3. 阶段一：收紧骨架叠加的可信边界

### 3.1 目标

把当前 `layout:'skeleton'` 从“能画出骨架”收紧为“明确知道什么时候只能诊断、什么时候可以进入正式验收”。

### 3.2 施工范围

主要文件：

- `src/animationReview.ts`
- `src/visualRig.ts`
- `src/poseGraph.ts`
- `src/animationCommands.ts`
- `src/server.ts`
- `test/skeletonOverlay.test.ts`
- `test/referenceOverlay.test.ts`
- 必要时补充 `docs/骨架叠加模式实施计划.md` 和 `docs/项目进展.md`

### 3.3 必做步骤

#### Step 1：统一 visualRig 入口

骨架叠加不得使用裸 `readJson(visualRigPath)` 作为正式依据。应调用现有 `requireVisualRig()`，继承：

- 版本检查；
- `confirmed` 状态检查；
- 角色/路径匹配；
- source fingerprint / mapping fingerprint；
- 15 个标准 role；
- 审查状态和证据要求。

如果诊断模式需要读取未确认 rig，必须显式标记 `diagnosticOnly: true`，且结果不能进入正式 review token 链。

#### Step 2：明确 correspondence 的唯一来源

不再使用“从多个 manifest 字段逐级猜测”的方式。输入优先级固定为：

1. 显式 `correspondence`；
2. 已确认的 pose/sequence 记录中绑定的 correspondence；
3. 找不到则 `metricsAvailable:false`，不自动推断左右身份、朝向或前后关系。

manifest 不具备该字段时，不能通过字段名 fallback 假装存在。

#### Step 3：拆分状态字段

骨架报告至少区分：

- `semanticMapped`：至少一个语义节点映射成功；
- `semanticComplete`：所有必需节点成功；
- `metricsAvailable`：metrics 实际可计算；
- `acceptanceEligible`：满足正式验收门槛；
- `unmappedRoles` / `mappingReason`：明确列出缺口。

保留旧字段时，只能作为兼容字段，不能让旧字段单独决定批准。

#### Step 4：定义正式验收门槛

当 `reviewAnimation` 的决策为 `approved` 时，如果本次使用 skeleton 证据，必须至少满足：

- `visualRig` 已确认；
- 目标角色指纹匹配；
- 必需 role 完整映射；
- `correspondence` 有来源、有内容；
- `metricsAvailable:true`；
- 视觉 GIF、原速 GIF、输入 manifest 和结构资产均进入 evidence；
- 任何 `unverifiable` 的必需指标都不能被当成通过。

诊断模式可以生成图，但只能产生诊断结果，不能生成正式批准令牌。

#### Step 5：修正 skeleton GIF 的叙述

报告中明确写：

- `skeletonSource: 'reference-single-frame'`；
- 当前是“单帧参考姿态 vs 目标动画逐帧骨架”；
- 不能宣称参考动画逐帧骨架对齐；
- 不能宣称像素级一致。

### 3.4 阶段一验收

- 未确认或指纹不匹配的 visualRig 在正式验收路径中被拒绝；
- 缺少 correspondence 时，metrics 明确不可用；
- 部分映射只能生成诊断图，不能批准；
- 完整映射的真实夹具仍可生成 skeleton GIF；
- `reference-above-target` 和 `overlay` 字节级回归不变；
- `npm run build` 通过；
- skeleton、reference overlay、相关 pose 测试通过；
- MCP 仍为 116 个工具。

### 3.5 阶段一停止条件

出现以下任一情况立即停止，不进入阶段二：

- 为了让测试通过而放宽 visualRig 或 correspondence 门禁；
- skeleton 结果仍能在缺少必需证据时生成 `approved` token；
- 既有两种布局的输出发生无法解释的变化；
- 真实资产中无法区分“部分映射”和“完整映射”。

### 3.6 提交点

建议提交：

```text

```

## 4. 阶段二：补足逐帧视觉关节点数据

### 4.1 目标

解决当前轨迹只有骨骼原点，无法还原 `visualRig.nodes[role].point` 非原点视觉关节的问题。

### 4.2 设计边界

不修改参考图的标注方式，不引入姿态估计模型，不在此阶段实现透视点控制。先把目标侧的“视觉点能否从 runtime 正确取出”做成可靠基础能力。

### 4.3 推荐数据形态

在预览 manifest 的每帧轨迹中增加独立字段，不破坏现有 `bones`：

```json
{
  "time": 0.0,
  "bones": {
    "arm1": {"x": 10, "y": 20}
  },
  "visualPoints": {
    "leftElbow": {
      "x": 12,
      "y": 24,
      "source": "boneLocal",
      "bone": "arm1",
      "localPoint": [3, 4]
    }
  }
}
```

原则：

- `bones` 保持兼容；
- `visualPoints` 是视觉关节层；
- 每个点记录来源和计算依据；
- 不把无法计算的点静默退化成骨骼原点；
- 后续可扩展 `meshTriangle`，但第一步优先完成 `boneLocal`。

### 4.4 必做步骤

1. 确认 Spine runtime 骨骼世界变换字段和坐标方向；
2. 为 `boneLocal` 节点实现“局部点 → 世界点”的计算；
3. 在 `previewRenderTools.ts` 生成逐帧 `visualPoints`；
4. 在 `animationReview.ts` 优先消费 `visualPoints`，仅在不存在时使用兼容的 `bones` 原点；
5. 记录每个 role 的来源、是否精确、是否降级；
6. 为非原点节点建立测试夹具；
7. 在 npc1 隔离副本中确认视觉点和渲染切片位置一致。

### 4.5 暂不实现

- 不根据 mesh 权重反推视觉关节；
- 不让 MCP 自动修改 mesh 权重；
- 不把 `meshTriangle` 在缺少三角形/权重证据时强行估算；
- 不把局部点轨迹直接等同于透视控制点。

### 4.6 阶段二验收

- 原点节点和非原点节点均有数值测试；
- `visualPoints` 与 runtime 实际渲染坐标一致；
- skeleton 叠加能绘制真实非原点关节；
- 缺少计算依据时明确标记不可用，不静默画在原点；
- 旧 manifest 没有 `visualPoints` 时仍可读取；
- 真实 npc1 通过至少一个非原点节点验证；
- `npm run build` 和相关回归通过。

### 4.7 提交点

建议提交：

```text

```

## 5. 阶段三：实现 depthPoints / 点状子骨骼透视映射

### 5.1 目标

把 `arm1-toushipoint` 设计从文档约定变成可校验、可映射、可被动画逻辑使用的结构能力。

### 5.2 核心原则

- mesh 权重仍由资产阶段完成；
- MCP 不刷权重；
- 特殊命名是辅助识别，不是唯一授权依据；
- 真实控制权限来自显式映射、父子结构和角色上下文；
- 点状子骨骼是透视控制点，不应被误判为普通肢体段。

### 5.3 推荐显式结构

在 mapping 中增加明确结构，命名可按项目约定：

```json
{
  "perspectiveChains": {
    "leftArm": [
      {"bone": "arm1", "perspectivePoint": "arm1-toushipoint"},
      {"bone": "arm2", "perspectivePoint": "arm2-toushipoint"}
    ]
  }
}
```

`-toushipoint` 只作为缺少显式字段时的候选提示，不直接授予写入权限。

### 5.4 必做步骤

1. 定义 `perspectiveChains` 的 schema、版本和状态；
2. 统一实体骨骼链、辅助点骨骼、末端骨骼的角色定义；
3. 校验实体骨骼和 point 骨骼的父子关系；
4. 校验 point 骨骼存在、唯一、未被错误归入普通链；
5. 把 `depthPoints`/`perspectiveChains` 接入 mapping 读取和确认流程；
6. 接入阶段二的 `visualPoints` 轨迹，让点状骨骼可被逐帧观察；
7. 实现稳定公式的纯数学模块：
   - `L' = L · cos(theta)`；
   - `Delta = L · (1 - cos(theta))`；
   - 位移作用于 point 骨骼，不直接改普通骨骼的 scale；
8. 增加正常缩放、IK、普通父子链和透视点并存的冲突测试；
9. 用真实资产验证“没有透视时不改变原动作，有透视时只改变指定 point 控制”。

### 5.5 骨骼链统一规则

不再由不同模块分别规定“必须正好三根”或“至少两根”。统一为：

- 语义层必须能得到上段、下段、末端三个角色；
- 真实骨骼层允许存在辅助骨骼；
- 每段实体骨骼可以有一个 point 骨骼；
- 所有实际父子关系必须通过校验；
- 不能仅根据数组长度判定合法性。

### 5.6 阶段三验收

- mapping 能明确返回实体骨骼和透视 point 的配对；
- 命名错误、父子关系错误、缺失 point 均能被拒绝；
- 未提供显式 mapping 时，命名只生成候选，不直接控制；
- 透视公式有独立数学测试；
- 普通 scale、IK 和透视 point 的边界行为有测试；
- mesh 权重不被 MCP 修改；
- 真实资产验证确认控制对象没有误伤普通骨骼。

### 5.7 提交点

建议拆成两个提交：

```text
feat: 增加透视点骨骼显式映射与校验
feat: 实现点状骨骼位移透视数学与动画应用
```

如果第二步尚未接入真实动画写入，则只提交第一步，不把“只读映射”宣称为“透视动画已完成”。

## 6. 阶段四：统一写入安全底座，但保留三种上层策略

### 6.1 目标

不是把普通写入、Host 提交、备份恢复强行合并成一个操作，而是让三条路径共用同一套底层安全零件，并明确权限边界。

### 6.2 底层能力统一

抽取或统一以下能力：

- 工作区路径和符号链接边界；
- 当前文件 hash / expectedHash；
- 文件锁；
- writer lock；
- 备份原始字节；
- 完整 JSON 校验；
- 原子写入；
- 写入日志和 requestId；
- 稳定错误码。

### 6.3 三种上层策略明确化

#### 普通动画写入

权限：只允许 `/animations/*`。

必须经过：版本、diff 白名单、官方规范、结构引用、dryRun、备份和 writer。

#### Host 候选提交

权限：只允许提交已经绑定候选 hash、review token、source hash、generation 和 authorization 的候选动画。
