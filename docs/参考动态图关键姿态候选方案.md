# 参考动态图关键姿态候选方案

> **状态：已实现候选阶段（不含自动批准）。** 2026-11-07 更新。`spine_analyze_reference_gif` 支持 `candidateMode:"keypose"`，`spine_extract_reference_keyframes` 支持从 manifest 读取候选；两者只输出可审查候选，不写入或批准参考姿态。

## 1. 问题与现状

用户判断：现有能力不足以识别目标参考动画的**节奏**与 **KEY pose**，必须补足。该判断成立。

源码核查（`src/referenceTools.ts`）：

| 工具 | 现状 |
|---|---|
| `spine_analyze_reference_gif` | 拆帧、统一画布、逐帧 SHA-256 像素哈希去重、记录 delay / 累计时间 / 循环标记 / 可见边界；`candidateMode:"keypose"` 额外记录帧间变化、包围盒运动、低速保持段和转折候选；`phases` **仍由 Agent 显式标注** |
| `spine_extract_reference_keyframes` | 默认均匀代表帧；`candidateMode:"keypose"` 合并均匀覆盖与速度局部极小、保持段端点、方向转折候选，结果仍需人工审查 |

即：当前产出的是 **representative frames（时间轴均匀代表帧）**，不是动画意义的 **key pose**（极值、转折、接触、重心转移、overshoot）。语义全靠 Agent 标注与后续视觉审查门禁赋予。

两个直接后果：

1. **漏掉落在采样间隙的关键瞬间**（如 walk 的脚部 contact 帧），且隐含"动作节奏均匀"假设，多数动作不成立。
2. **节奏信息失真**：`estimatedPeriod` 目前直接取文件总时长，报告自身已警告"需 Agent 确认是否完整循环"；GIF 帧延迟常被导出器归一化、零延迟被 `delayCorrected` 兜底为 100ms，不足以单独还原节奏。

## 2. "平均帧截取 + 逐帧差异曲线"方向对，但直接用会错

用户提出两者综合使用。**方向正确，两者确实互补**（均匀取样保证时间覆盖，差异曲线提供事件点）。但"把差异曲线的峰值当作 KEY pose"是一个必须纠正的概念错误。

### 2.1 帧间差异是"速度"，不是"姿态极值"

设肢体位置 `x(t) = sin(t)`，逐帧位置差 `|Δx|` 就是速度。最小实验实测：

```
帧差(速度)最大处: t=3.141, x≈0.000  -> 肢体经过中位，是过渡帧
帧差(速度)最小处: t=1.555, x=1.000  -> 肢体到达极值，是 KEY pose
姿态极值实际位置: x=+1 在 t=1.571,  x=-1 在 t=4.712
```

**运动最快的帧恰恰是 inbetween / breakdown，运动最慢（停顿、反转）的帧才是 key pose。** 若按"差异峰值"选帧，会系统性地选出中间过渡帧而漏掉真正的姿态极值——比等间隔取样更糟，因为它带着"已优化"的假象。

正确对应关系：

| 差异曲线特征 | 动画含义 | 是否 KEY pose |
|---|---|---|
| 局部**极大**（高速） | 快速过渡 / inbetween | 否 |
| 局部**极小**（停顿、零速） | 姿态极值、保持、接触 | **是（候选）** |
| 二阶变化 / 方向反转（加速度峰值） | 运动方向改变、发力点 | **是（候选）** |
| 连续零差异段（hold） | 静止保持 | **只取端点**，段内每帧都不是 |

### 2.2 像素差异的干扰源

全画面逐像素差会混入非姿态变化：相机运动、背景/特效、粒子、光照闪烁、压缩抖动、循环接缝。项目现有 warning 已自承："**相机运动与角色运动不能仅凭拆帧自动区分**"。

因此差异计算**必须限定到角色区域**，不能直接用整幅画布。

## 3. 修正设计

### 3.1 差异计算：逐帧 ROI，而非全画面

- 现有 `bounds` 是**所有帧的并集**（全局 min/max），过宽。改为**逐帧可见包围盒** `frameBounds[i]`（alpha 非 0 像素范围）。
- 差异度量用「统一画布上、两帧各自 ROI 的**并集区域**内的像素差」，避免角色位移导致的 bbox 抖动被算成变化。
- 同时输出两个分量供判别：`appearanceDelta`（像素差）与 `bboxMotion`（包围盒中心/尺寸变化）。二者比值可辅助判断"是姿态变化还是整体平移/相机运动"；**不据此自动下结论**，只作为报告证据。

### 3.2 从差异曲线到关键姿态候选

1. 生成速度曲线 `v[i]`（§3.1 的加权差异），做轻量平滑抑制压缩噪声。
2. 找 **v 的局部极小**（停顿/极值）与 **v 的方向反转点**（加速度/曲率变化），作为"姿态事件"候选。
3. **合并 hold 段**：连续 `v < 静止阈值` 的区间只保留首尾端点，段内帧全部排除——否则静止段会因"速度小"而聚集出大量假关键帧。
4. 明确**排除 v 的局部极大**（过渡帧），不纳入候选。
5. 每个候选记录：帧索引、时间、`v` 值、判定类型（极值/反转/hold 端点）、证据说明。

### 3.3 节奏周期估计（解决"节奏"诉求）

- 对 `v[i]` 做**自相关**或统计显著峰间距，估计运动周期 `estimatedPeriod`，替代当前"文件总时长"。
- 同时输出 `periodConfidence` 与依据；**低置信度时明确标注不可用作循环判断**，交回 Agent。
- 保留现有 `loop` / `delayCorrected` 证据，不覆盖原始帧延迟数据。

### 3.4 均匀取样 + 显著候选的合并策略

两者不能简单取并集（帧数爆炸、失去时间覆盖）。建议：

| 步骤 | 做法 |
|---|---|
| 保底骨架 | 均匀取样 `count × 保底比例`（建议 0.5，至少 2 帧，含首尾），保证全时段覆盖与循环闭合 |
| 候选插入 | 按 §3.2 的显著性评分排序，依次插入显著候选 |
| 最小间隔去重 | 与已有选中帧时间间隔小于阈值的候选跳过（防相近帧堆叠） |
| 总数上限 | 仍受 `count`（2–32）约束，超限时按评分截断 |
| 输出标记 | 每帧标注来源 `uniform` / `salient`，以及是否被人工调整过 |

### 3.5 输出结构（建议）

```json
{
  "candidates": [
    { "index": 12, "time": 0.24, "source": "salient",
      "kind": "velocityMinimum", "score": 0.83, "v": 0.012,
      "reason": "速度局部极小，疑似姿态极值" },
    { "index": 0, "time": 0.0, "source": "uniform", "kind": "coverage", "reason": "时间覆盖保底" }
  ],
  "timing": { "estimatedPeriod": 0.8, "periodConfidence": 0.72, "method": "velocityAutocorrelation" },
  "velocityCurve": [ ... ],
  "warnings": [ "候选不自动成为 KEY pose；阶段与语义须 Agent 标注并经视觉审查。" ]
}
```

### 3.6 门禁（不可省略）

- 产出**一律是候选**，不是 KEY pose。沿用现有链路：`spine_create_reference_pose` 标注 → `spine_review_reference_pose` 审查 → `spine_upgrade_reference_pose` 补证据 → `spine_create_pose_sequence` 记录阶段。
- `phases` 仍由 Agent 显式标注，不自动推断；符合 `AGENTS.md`「图片坐标不可直接传入目标 IK」「不凭空生成」原则。
- 候选筛选结果须附**逐项理由**，不批量套用统一文本（沿用项目既有审查规则）。

## 4. 验证判据

实施后须用带人工标注的参考 GIF 做回归，而不是只看"能跑通"：

| 指标 | 判据 |
|---|---|
| 关键姿态召回 | 人工标注的极值/接触帧被候选覆盖的比例 |
| 假阳性 | 候选落在过渡帧（原差异峰值）的比例应显著低于纯峰值法 |
| hold 段 | 静止段内部不得聚集多个候选 |
| 周期估计 | `estimatedPeriod` 与人工确认周期的偏差，低置信度须正确标注 |
| 节奏还原 | 候选时间戳与人工标注阶段时间的偏差 |

## 5. 实施边界

- **纯只读**：只扩展 manifest 与候选输出，不新增任何写入能力，不触碰 V1 边界。
- **不引入姿态估计模型**：本方案基于已有逐帧 PNG 做像素级分析，保持轻量离线。引入 OpenPose / DWPose / GVHMR 等属于另一条路线（见§6），需另行评估模型依赖、输入域匹配与 `AGENTS.md` 限制。
- **不自动批准**：与 Salient Poses 等成熟算法不同，本方案不做全局最优重建，只提供**可审计的候选 + 证据**，判定权归 Agent 与视觉审查。
- **口径修正**：`spine_extract_reference_keyframes` 应更名为"候选代表帧"，或在描述中明确**它不是 key pose 识别**，避免后续链路建立在错误前提上。

## 6. 同行做法核查（含对本文此前论断的修正）

### 6.1 修正：此前"成熟方案都建立在已有骨骼/关键点轨迹之上"的说法是错的

正确表述应为：**它们并不天生拥有这一层，而是专门用了一个 stage 把这一层从视频里造出来。** 把"我们先没有"说成"别人天生有"，会误导为"这条路对我们封闭"；真实情况是"这条路要额外付一个 stage 的成本"。路线取舍的依据应是**输入域是否匹配**，而非能力是否先验存在。

### 6.2 同行实际存在三条路线，其中两条不做"自动划分 key pose"

| 路线 | 代表 | 怎么做 | 是否自动划分 key pose |
|---|---|---|---|
| **A 先造轨迹，再做数值 beat 检测** | `mixamo-llm-mocap`（GVHMR → SMPL-X → 33 landmarks → `analyze_landmarks.py` → action_spec → Blender MCP） | 视频 → 姿态估计 → 密集关节轨迹 → 数值检出 beat | **否**。产出的是**语义节拍表**（support schedule 哪只脚着地、rest blends、fist states），不是 Salient Poses 意义上的 key pose 集合。其信条是"beat 决策来自数字，绝不靠肉眼看帧" |
| **B 交给多模态模型看** | `blender-animation-mcp`（`setup_video_reference` / `render_video_overlay` / `inspect_video_overlay` / `video_frame_offset`） | 视频叠在视口上 + 时间轴对齐 + 联系表 + 数值回读，**由模型自己识别并对骨骼打关键帧** | **否**。官方推荐循环写明"在**触点附近、极限姿态处**或明显不连续的位置，用 `render_frame` 渲染检查"——触点与极限由**模型视觉判定**，无检测算法 |
| **C 纯像素运动分析** | 学术：光流 → motion energy → 局部极值（Frontiers 2017）；`dM/dt` 极值（KFSENet） | 不需要骨骼 | 是，但目标是**动作识别**而非动画 keying（见 6.4） |

**关键事实：与我们最可比的同行（blender-animation-mcp）根本不做 key pose 检测**，它的定位就是"让多模态模型能看见自己做的动画，而不是只对着 transform 数字推理"。它提供的正是**基础设施**：overlay 对齐、联系表（上限 25 帧）、逐帧渲染、世界变换采样。

### 6.3 路线 A 对本项目的适用性：输入域不匹配，暂不适用

- 硬性输入要求：**锁定机位、T-pose 首尾标定、干净背景、全身可见、约 8GB VRAM**。
- 姿态估计在风格化 2D 图上**默认失效**。Meta `Animated Drawings` 明确记载："Most AI models trained on photographs perform poorly on children's drawings... Meta's system was fine-tuned on millions of amateur sketches"。即照片训练的模型用于风格化图像需要专门 fine-tune。
- 且 `Animated Drawings` **并非从参考动画提取关键姿态**，而是把**预设 MoCap（BVH）重定向到静态画**——它绕开了本问题；其 GitHub 仓库已于 2025-09 归档（只读）。
- 本项目参考素材多为像素/二次元精灵 GIF，与上述输入分布差异大。故路线 A 列为**不采用的下一阶段候选**，不设为本方案前置。

### 6.4 路线 C 与本文设计的分歧点（须记录，勿照搬）

Frontiers 2017 的做法是：Lucas-Kanade 光流 → `E_flo(t) = Σ‖u‖` → 高斯平滑 → 取**局部极大与极小** → 再用 **extent 过滤**（bbox 宽/高需 > (1+λ)·参考 extent）。

- **它同时取极大和极小**，本文只取极小（速度极小 = 反转 = 极值姿态）。原因是**目标不同**：它服务于动作识别，要挑**最具判别力**的姿态；本文服务动画 keying，要**所有**反转点。
- **extent 过滤对动画是有害的**。以开合跳为例：张开姿态 extent 大且速度≈0（保留），收拢姿态 extent 小且速度≈0（被过滤掉）——而收拢/接触/中性极限恰恰是动画必须的关键姿态。**过滤会系统性丢掉一半关键姿态**。
- 本文因此保留"速度极小 = 候选"，把 extent 降级为**输出证据之一**而非过滤条件。

### 6.5 定位结论

同行没有"从视频自动划分 key pose"的通用解法。务实组合是 **B 为主（模型视觉判定 + 审查门禁）+ C 为辅（像素运动能量提供可审计候选与节奏证据）**，路线 A 待输入域匹配时再评估。

本项目当前**已有 B 的骨架**（逐帧渲染 + 视觉审查门禁），缺两项：

1. **B 的基础设施**：视频/参考帧与工作产物的**叠加对齐**（对应 `render_video_overlay` / `video_frame_offset` 的角色）。当前只有并排对比，没有叠加。
2. **C 的候选提议器**：即本文§3 设计，仅作候选，不替代判定。

> 本节的核查依据为公开仓库 README 与论文，未在本机运行任何姿态估计模型；路线 A 对像素/二次元素材的实际失效率**未经实测**，属基于训练分布差异的推断，落实前需实测验证。

## 7. "直接让模型读视频"在 MCP 中不存在；抽帧正是省 token 的手段

### 7.1 协议事实：MCP 没有视频内容类型

实测本项目依赖的 MCP SDK 类型定义（`node_modules/@modelcontextprotocol/sdk/dist/esm/types.d.ts`）：

- 工具返回的内容块只有 `TextContent` / `ImageContent` / `AudioContent` / `EmbeddedResource`（采样侧另有 `ToolUseContent` / `ToolResultContent`）。
- 全文检索 `video`：**0 次命中**。

因此"把参考视频直接交给大模型"在 MCP 协议内**无法实现**。模型消费视频的唯一途径就是**逐帧当作图片送入**。`blender-animation-mcp` 的 `setup_video_reference` 实际做的是把 MP4 **加载进 Blender 视口作背景**，再由 `render_video_overlay` 将"参考帧 + 当前 rig 渲染"合成后以 **MCP image content** 返回——模型读的仍然是图。

### 7.2 因此"抽帧 vs 读视频"这个对比不成立，且省 token 的是抽帧

模型处理参考动态素材的成本 ≈ **帧数 × 单帧成本**。等间隔抽 8 帧是 8 份；若把一段 60 帧 GIF 全量送入则是 60 份。抽帧**本身就是节省 token 的手段**，不是因能力不足而做的妥协。

同行的差异不在"抽不抽"，而在**抽得更聪明**：按需、可指定任意帧、合成叠加。叠加图还把"参考 + 产出"两张并排压成一张，进一步省。

### 7.3 查到的实际差距（比预想更靠前的一环）

| 维度 | `blender-animation-mcp` | 本项目现状 |
|---|---|---|
| 取帧方式 | 模型**按需指定任意帧** | 固定 8 帧等间隔，**不可指定** |
| 对比形态 | **overlay 叠加**合成 | 并排 |
| 时间轴对齐 | `video_frame_offset` 显式对齐 | 无 |
| **参考帧是否回传图片** | 是（MCP image content） | **否** |

最后一行是本次新查出的具体问题：`src/referenceTools.ts` 中两个工具只做 `writeFile(...frame-*.png)` 后返回 JSON 报表（含 `manifestPath`），**未设置 `__images`，也未产出 `pages` 字段**。而项目**已有**通用图片回传机制（`server.ts:1003-1010` 的 `pickImages()`，读取 `__images` 数组与 `pages[].clean`，上限 3 张并以 base64 作为 image content 返回），渲染类工具在用，**参考类工具没用**。

后果：模型调用 `spine_analyze_reference_gif` 后拿到的是一份路径清单，需**自行再去读取那些 PNG** 才能看到画面。这比"抽帧策略粗糙"更靠前——抽出来的帧没有递给模型。

### 7.4 应补的三项（按成本排序）

1. **让参考工具直接回传图片**：复用现有 `pickImages` / `__images` 机制，`analyze_reference_gif` 与 `extract_reference_keyframes` 把选中帧路径填入。**改动最小、收益最直接**。
2. **支持按需取任意帧 + overlay 合成**：对齐 `render_frame` / `render_video_overlay` 的角色，让模型只取可疑帧而非固定 8 张，且叠加对比替掉并排。
3. **时间轴 offset 对齐**：解决参考与产出的相位对齐。

三项均为只读、不触碰 V1 写入边界。token 影响：第 1 项持平，第 2、3 项应为**净减少**（按需取帧 + 叠加压帧）。`pickImages` 现有 3 张上限是既有 token 护栏，保留。

## 8. 叠加对齐：本项目不是"能不能学"，而是已完成九成

### 8.1 结构上我们比 `blender-animation-mcp` 更容易做到

`src/rasterRenderer.ts` 使用 `@napi-rs/canvas`，`rasterFrame(skeleton, images, bounds, width, height, background)` 由**本项目自己**绘制。而 `blender-animation-mcp` 必须哄第三方 DCC 把视频挂成视口背景、再截取视口。

即：它们要说服 Blender 支持背景层；我们只需要 `ctx.drawImage(参考帧)` 垫在骨架下面。**渲染管线在我们手里，这是优势而非劣势。**

### 8.2 实测：对齐与时间映射已经实现，只差"上下排列 → 叠加"

`src/animationReview.ts:13 renderAnimationComparison` 现状（已通读实现）：

| 能力 | 是否已实现 | 依据 |
|---|---|---|
| 加载参考帧入同一 canvas | ✅ | `loadImage(readFile(f.filePath))` 后 `ctx.drawImage(...)` |
| **空间对齐**（缩放/偏移/裁切） | ✅ | `rs = poses.targetScale * poses.standardHeight / view.height`；`refX = w/2 - view.crop[2]*rs/2`；`refY = h*.9 - (view.groundY - view.crop[1])*rs` |
| **时间对齐** | ✅ 且强于同行 | `phaseMap`（`targetTime ↔ referenceTime` 分段线性插值，含严格递增与全覆盖校验）——**比 `video_frame_offset` 的单一常量偏移更强** |
| 逐帧同步出图 | ✅ | 按 `target.frames` 逐帧取 `referenceFrameAt(rt)` |
| **叠加** | ❌ | 布局为 `reference-above-target`，canvas 高 `(h+28)*2`，参考在上带、目标在下带 |

结论：从现状到"参考帧 + 当前 rig 叠加"，**差异只是画布布局**：高度由 `(h+28)*2` 改为 `h`，目标帧以 `globalAlpha`（`rasterRenderer.ts:96` 已使用该能力）叠在参考帧之上，而非画到 `y=h+28`。

### 8.3 实施时须一并处理的两处

1. **审查门禁硬编码布局名**：`animationReview.ts` 中 `record.requiresReferenceComparison && m.layout !== 'reference-above-target'` 会直接抛错。新增 overlay 布局时必须让该校验接受新布局（或并行保留原布局），否则新图无法通过审查。
2. **叠加可见性**：直接全覆盖会互相遮挡。需提供 `opacity`（骨架半透明压在参考上）或差值/描边模式，不能只有一种。

### 8.4 定位

本项属**只读渲染与对比**，不触碰 V1 写入边界，与 Host 是否 attached（当前 `observer` 模式）无关——`previewRenderTools` 直接读盘渲染，不依赖 Host 写权限。

因此 §7.4 的第 2 项（按需取帧 + overlay）应重新表述为：**不是从零新建，而是把已存在的对比渲染从"上下排列"扩展出一种"叠加"布局，并对外开放为可单独调用取任意帧的能力。**
