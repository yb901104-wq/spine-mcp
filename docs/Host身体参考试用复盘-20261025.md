# Host 身体参考试用复盘

日期：2026-10-25，北京时间。对象：用户提供的 171 帧、5.88 秒身体参考 GIF，目标角色 npc1。本文是对实际执行的复盘，不是新施工单，不修改现行比较策略或批准条件。

## 结论

1. 新 Host 已补齐有实际价值的工程状态、明确版本、内存编辑、撤销、回放和事务基础；旧项目本来就有实际 MCP 服务，演进不是从「假 MCP」变成「真 MCP」。
2. **本次并未主要使用新的持续编辑方式。24 次 MCP 调用中，21 次仍走 detached 文件流程；Host 的 3 次调用是打开失败一次、打开成功一次、截图一次，没有 Host 编辑调用。** 本轮不能作为新载体节省时间或 token 的成功证明。
3. 本轮实际用时约 **22 分 10.6 秒**，只得到一个被退回的起始帧候选，没有完整身体动画。工程实现完成和用户创作目标完成必须分别判断。
4. 失败不只是「再调几次参数」：现有标注、固定角色比例与部分硬性比较条件存在可计算的冲突；同时还有标注不确定性、求解变量覆盖、工作流组织和反馈呈现问题。
5. 与成熟编辑器 MCP 的主要差距，已经转向**可直接使用的创作工作流、领域能力和成品验证**。继续增加连接接口，不能单独补上这些差距。

统计依据：[不可覆盖的复盘指标与证据索引](plans/host-body-reference-retrospective-20261025.metrics.json)。原始试用：[动作尝试记录](plans/host-body-reference-trial-20261025.md)。

## 1. 新旧模式究竟改变了什么

| 方面 | 旧文件模式 | 当前 Host 具备的机制 | 本次实际使用情况 |
|---|---|---|---|
| 操作对象 | 各工具接收路径，读文件并保存新修订 | 受管工程、活动文档、完整版本和依赖绑定 | 主创作仍用路径，最后才打开 Host |
| 连续修改 | 新路径、求解和报告串联；已有高层批量工具 | 当前内存原子修改、自动求解/发布、撤销/重做 | 本次没有调用 Host patch、undo 或 redo |
| 参考适配算法 | 已有方向初值和 60 次有界修正 | attached/detached 共用计算内核 | 主要仍调用旧入口，算法不会因换载体自动变好 |
| 实际画面 | 离线图/GIF、预览资源与共享会话 | 图片绑定明确文档版本、候选、资源、相机及 runtime 回读 | 最后真实 player 截图已验证，这是本轮确实使用的新价值 |
| 保存与恢复 | 工作流文件分散，角色写入有原备份/规范门禁 | 唯一 Writer、精确授权、原子发布、journal 和幂等恢复 | 没有提交动画，本轮未验证该段完整链路 |
| 工程组织 | Agent 串联 mapping、rig、参考、pose 和报告 | manifest 与资产绑定可检查一致性 | 仍需临时写 sequence、补工程清单；预览首次被绑定门禁拒绝 |
| 使用入口 | 可调用底层工具，但编排工作多 | C2 工程链路在隔离研发配置中可用 | 依赖 5 个临时 JS 脚本及多份操作清单，尚未成为日常入口 |

应承认两点：旧模式已有单次批量编辑和单调用内部多次迭代，不能把新 Host 的价值描述为一律「多调用变一次」；新 Host 的真正新增价值是**同一编辑状态上的一致性、连续反馈和可逆操作**，这次没有充分使用。

实现依据：`src/poseOps.ts:batchPoseOps`、`src/hostClient.ts:patch/history/assetCommand`、`src/referenceRetargetKernel.ts`、`src/hostEvaluator.ts`。生产默认仍是 C1；隔离 C2 并不是普通 CLI、页面或审批文件可以直接切换的生产功能。

### 2.1 本轮实测

统计从完整 GIF 请求开始，不包含此前静态 PNG 补传、头手局部演示、性能施工，也不包含当前复盘。

| 指标 | 结果 | 解释 |
|---|---:|---|
| 请求到最终回复 | 22 分 10.6 秒 | 10-24 23:50:53.694 → 10-25 00:13:04.274，含读源码、看图、脚本编排、等待与客户端调度 |
| 第一到最后 MCP 调用回执跨度 | 18 分 42.8 秒 | 不是各调用运行时间之和 |
| 模型请求 | 30 次 | 当前聊天该回合实际用量记录 |
| Agent 外层工具交互 | 29 次 | 26 次 exec、3 次浏览器 js；与下面 MCP 计数不是同一层，不能相加 |

| stdio 会话 | 10 次 | 从执行脚本统计：8 批文件流程、2 次预览尝试，每批重新连接 |

| 完整身体动画交付 | 0 段 | 1 个起始参考姿态诊断，随后退回 |

仅从连续脚本回执间隔看，动作级验证到 60 次修正结果约 1.14 秒；这包含文件写入和脚本调度，只可作该调用的邻接间隔观察，不能冒充独立 CPU 计时。没有证据把 22 分钟归因于求解器本身很慢。

读取的是当前聊天本地 `token_usage_record`，按唯一 `response_id` 汇总 30 条，并与该回合最终累计值核对一致；未读取其它聊天，也未用字符串长度冒充 token。

| 非缓存输入 | 86,458 |

这表示长历史在 30 次请求中被反复处理，**不表示本次新增了 669 万输入内容，也不表示有同等数量的非缓存消耗**。非缓存输入也可能含缓存未命中的旧上下文。上述用量涵盖图片、源码阅读、脚本、报告与历史提示，不能全算成 MCP 或 Host 的成本；没有对账单金额作验证。

返回体还存在改进空间：24 份调用记录共约 2.08MB；结果对象去空白后重序列化合计 844,327 字符，不含单独图像块。一次 Host open 为 297,333 字符，两次 solve 各约 165,000 字符，含重复的 visual/顶点、numeric、state、capabilities。大部分结果被临时脚本缩成摘要后才打印给模型，所以这些完整字符量不能直接换算成本轮模型 token；但表明标准接口仍缺少默认的精简返回。

### 2.3 能否证明比旧模式省了多少

**目前不能。** 找到的旧文件流程记录分别有 23 次和 26 次调用，但使用的是旧攻击参考，还包含多阶段参考升级或诊断动画导出，与本次坐地身体参考不是同任务。旧样本缺同口径墙钟和模型用量，不能据 23/26 对 24 得出提升或退步百分比。

此前 state/frame P95 12.39/25.51ms 属于已登记固定站姿动画、三进程 90 样本的专门基准；它说明特定读取负载达预算，不能外推本次参考任务，也不能把毫秒级出图与 22 分钟创作墙钟混为一谈。

要得到有效结论，应冻结同一 GIF、角色、mapping、rig、参考标注、起始姿态、比较策略与构建，分别执行 detached 和 attached；同样计入或排除准备工作，使用相同模型和可比上下文，记录每步起止时间、调用、结果大小、模型缓存用量和最终质量。不能让新模式复用旧模式准备成果、再把准备时间全记给旧模式。

## 3. 本次失败的原因

### 3.1 本轮左臂约束存在局部不可满足条件

在本轮已固定的标注、链长和躯干通道下：参考左臂弯曲角约 63.43°，允许误差 15°，所以目标最多弯至 78.43°。目标上臂和前臂分别为 0.6136、0.3700 个躯干长。

二维两段链的肩腕距离为 `sqrt(a²+b²+2ab*cos(弯曲角))`。在上述弯曲范围内，目标肩腕距离最短约 **0.7775**；但参考肩腕距为 0.5064，现行距离门限只允许目标最多 **0.6564**。两个区间没有交集。

因此，在这些输入条件保持不变时，继续迭代不能让左肘角与手腕伸出距离同时通过。这里的结论限于**本轮遮挡估计、固定比例与当前约束组合**，不能推导为角色整体不可能做这个动作，更不能自动改变门限。之前仅说「需要改进适配」不够具体；还必须先检查标注语义和约束是否相容。

### 3.2 参考标注有不确定性，但求解仍把它作为精确目标

参考肩、肘、髋、膝多数藏在宽袖和衣摆内，置信度约 0.4–0.6。工具保留了遮挡与推测字段，但当前比较/残差并未把这些值转换成不确定范围或敏感性分析。Agent 标注后登记 approved，只说明完成了当前流程，不能增加不可见关节的真实可知程度。

参考 head 使用面部整体中心，目标 head/face 使用既有骨骼/嘴部锚点，语义也并不完全相同。头部方向已降为诊断，但手到头的距离仍为必要指标，这可能继续混入体型和锚点选择差异，需要单独核对。

### 3.3 求解策略缺少可满足性预检和硬条件处理

初值先按参考分段方向与目标自身链长生成，再按参考相对躯干的手位评分；对于不同身体比例，两种目标可能冲突。求解前没有先发现此类冲突。

当前局部修正变量包含 body 和手脚目标；torso 通道在方向初值阶段调整后不进入后续优化，head 也不在变量中。这限制了搜索空间，但不能直接认定增加变量就会解开上述比例冲突。

轮廓内外等二元指标按现行规则只做门禁、不进入连续残差，这是明确的设计约束。当前修正仍主要接受总残差改善，缺少针对硬边界的可行候选处理，最后可能得到连续分数较优、必要轮廓关系仍失败的结果。应改进约束处理与解释，而不是把二元值硬塞进最小二乘。

另有策略口径需要核对：`poseGraph.ts` 的旧 `arm.*.wrist` 仍按各自臂长归一，新 `wristReach` 按躯干长归一，二者均参与必要判定。旧项究竟表达方向形状还是长度，需与 AGENTS.md 的统一躯干归一要求对齐。本轮仅记录，不修改既有结果或规则。

### 3.4 工作流与本次执行方式增加了负担

- 新 Host 没有成为创作主会话。绝大多数姿态和参考操作仍先在文件中完成，最后才挂到载体上，新增版本/撤销机制没有得到本轮验证。
- Agent 读取了较多源码，编写了 5 个临时 JS 脚本，另写 sequence、操作清单和工程绑定。这些编排应逐步由稳定的受控工作流承担。
- 本轮 Host 首次打开因缺少 visualRig 等工程声明被拒绝。门禁正常，输入准备不完整；这是本次执行和工程登记流程的问题，不是封闭 Spine 导致的失败。
- 通用 Host 页直接显示「数值通过」，没有在主要状态中突出「参考关系 5 项失败」。另写结果 HTML 后才清楚呈现，说明载体主反馈还不够完整。
- 用户要验证按参考做特定身体动作，执行中直接采用现行严格几何比较，没有先解释不同体型下「动作转译」与「几何复刻」的区别。遵守现行规则是正确的，但缺少提前说明和可行性判断。

### 3.5 哪些原因本轮没有证明

没有证据表明本轮卡在 MCP 连接、JSON 规范、备份、Spine 导入或后半段动作资源能力；这些环节尚未全部执行。坐地、低头、起身的视角与切片表达能力也未验收。初始帧失败后停止是现行规则的结果，不能据此宣称整段动作在任何合理适配方法下都做不成。

## 4. 与成熟类似 MCP 的差距

本节对照维护者源码/文档，不安装外部编辑器、不声称相同任务的性能倍数或成功率。Unity、Blender 是主要编辑器桥接参照；Godot、Aseprite 用于补充 2D 机制，不把所有社区项目统一认证为成熟产品。

| 机制 | 外部参照 | 当前差距或已有价值 |
|---|---|---|
| 活动创作状态与实际回读 | Unity 的 editor_state；Blender 插件中的场景与视口 | Host 已具备对应基础，但本次主要创作仍在载体外完成 |
| 可发现的能力与简洁上下文 | Unity v10.3.0 按会话激活工具组，状态含阻塞与下一步建议 | 已有 capabilities/readiness；101 个工具未形成按任务精简的发现方式，部分返回重复且过大 |
| 连续动画编辑和即时观察 | Godot AnimationPlayer 的创建、轨道/关键帧、播放/定位回读 | 已有受限 pose/motion/skeleton 和时间选择，但有效控制范围、工程登记与失败修正仍需更多人工编排 |
| 完整工作流与批量组织 | Aseprite 示例提供工作流、批量操作、测量和可再次编辑的文件 | 本项目有高层函数和原子姿态批次，但本次仍靠临时脚本拼接，缺少稳定的参考创作会话 |
| 创作内核 | 上述桥接利用已有 Blender/Unity/Godot/Aseprite 数据与编辑能力 | 本项目接入 runtime 不能得到 Spine 编辑器完整创作内核，需要自行承担姿态语义、适配、历史和导出；这是主要投入差距 |
| 安全提交与恢复 | 各项目选择不同机制，批处理不必然原子 | 本项目版本、备份、唯一 Writer、授权与恢复较细，是已验证的工程价值；不能据此宣称整体成熟度更高 |
| 日常部署与交付 | 参照项目提供安装/连接及编辑器内使用路径 | C2 仍隔离研发，便携包未更新；真实完整动作、第二角色、独立 Spine 导入和长期观察未通过 |

关键区别不是「有无常驻 Host」：Aseprite 的文件/批处理路线同样可以形成有效工作流。真正要比较的是**Agent 能否使用明确命令，持续产出可检查、可再次编辑的结果，并以可控成本完成用户任务**。反过来，Blender/Unity MCP 的存在也不自动保证其能把这段 GIF 正确重定向；它们不能作为本任务质量必然成功的对照组。

## 5. 建议的后续顺序

1. **先修验证设计与计量。** 将载体可靠性、参考适配质量、完整动画交付分成三组；增加每阶段任务 ID、起止时间、调用、简洁结果与产物指针。按同一冻结输入做新旧模式 A/B，包含准备成本且不隐去失败。
2. **让 Host 真正承接一次参考编辑会话。** 工程/参考/rig/姿态登记、打开、编辑、失败诊断、看图、修订和重开由标准受控入口串联，保持一个可持续会话；不靠 Agent 写临时项目胶水。默认只返回当前状态与失败摘要，完整顶点和证据按需读取；主界面突出数值、参考、视觉和导入各自状态。
3. **解决适配问题后再扩段。** 先核对关节语义与遮挡敏感性，再做约束相容性预检和硬条件求解；明确严格参考复刻与按目标体型表达动作的需求契约。任何策略变更应单独讨论、版本化并补真实反例，不能针对本样本自动放宽，不能改回各自臂长归一来吸收差异。
4. **用同一 GIF 完成真实交付。** 起始姿态通过后，逐阶段验证坐地/低头/起身、完整节奏与过渡，最终输出当前 player、原速动画、参考对照和可导入 JSON，并独立检查 Spine 导入。完整结果才是创作能力验收。

现阶段可以表述为：**工程基础明显增强，但本次实际工作方式变化有限，创作效率提升尚无同任务证据，按参考完成动画的核心能力仍未验收。** 这不能用单一完成百分比表达；需要补上的既有工作流集成，也有参考动作适配这层领域能力。
