结论：载体的版本、状态、回放与事务基础已经补齐较多，下一阶段的工作重心应转到**创作工作流、可用动作控制、简洁反馈和真实交付**。基础施工接近尾声，不等于参考动画创作已具备日常可用性；也不需要继续把所有问题归为“再造一个更大的载体”。

本轮已执行的改动仅为用户明确要求的观测降级：可靠刚性轮廓/误差圆优先，遮挡时退回两个既有节点连线并返回近似数值。下列其余改进是逐项复查后的方向与验收建议，不计作已实现。

## 1. 观测策略：必须能给出当前条件下可用的结果

此前把增强观测设为必需门禁，导致已有两点估计却因缺轮廓停住，这个设计过严。现改为策略 v2：

| 输入情况 | 返回结果 | 后续处理 |
|---|---|---|
| 刚性轮廓、误差圆和方向一致，均可靠 | contour / measurable | 使用轮廓主轴与误差界，继续严格比较 |
| 轮廓被遮挡、是衣袖、近圆、误差圆未取得，但两个既有节点可用 | twoPoint / estimated，返回数值方向 | 继续原两点流程；显示近似来源，未知误差保持 null，不新增必需轮廓门禁 |
| 两个必要节点也未知或重合 | unavailable，列出缺项并保留可取得的其它部件结果 | 不编造坐标；可保留已有候选，但该部件不能冒充已匹配 |
| 可靠轮廓与可靠端点明确矛盾 | conflict，保留两份方向与原因 | 复核标注，不能自动选择更容易通过的一份 |

实际参考复测已经通过真实 MCP 返回：左上臂图像方向 **45°**、左前臂 **-18.43495°**，均 twoPoint/estimated、uncertaintyKnown:false；参考和源输入未改。[复测记录](plans/reference-fallback-20261025.json)。这是可用的近似方向，不是动作批准或三维角度。

含 parts 的图/审查记录绑定策略 v2，旧批准不继承。原 segment 角度、身份、支撑和接触等动作门禁仍执行。“有结果”意味着给出当前最佳候选和具体未满足项，不等于把失败标成成功。

## 2. 旧问题中已补齐的部分

| 历史问题 | 当前复查结论 | 当前依据与剩余范围 |
|---|---|---|
| 没有真正的 MCP，只会改文件 | 已有真实 SDK/stdio、schema 和协议回归，不能继续这样描述 | `server.ts`；resources/prompts、roots、logging 与错误也已实现 |
| 没有可重开的工程模型 | 核心已实现 | `projectModel.ts/projectSchema.ts`；剩余是建立工程时仍需较多编排 |
| 没有活动文档、版本或内存真相 | 核心已实现 | Document Store、snapshot、VersionRef、attached/frozen 规则；实际使用还需默认走这些入口 |
| 每次查询都重新求解/构造全部 runtime | 已部分解决 | `poseDigest` 零求解、LRU 模板/图像复用、独立 Skeleton；默认返回大小与新负载仍有问题 |
| 修改、看图、撤销各是脱节的文件操作 | 隔离 C2 已接通 | 同版本 patch→求解→回放→frame，undo/redo、新修订保存与重开；参考任务编排尚未产品化 |
| 画面与输入不一致、截图不能证明来源 | 有完整分层核验 | runtime 矩阵/顶点、candidate/hash、相机、版本与真实 player；Canvas mesh 等价仍单列 |
| 写入无事务/恢复 | 已有较完整基础 | 唯一 Writer、白名单、备份、授权、journal、幂等和恢复，不需要继续无边界扩建 |
| 所有计算都混在工具入口 | 已抽出共享核心，仍需收敛适配层 | `animationKernel/animationCommands/retargetEngine`；`server.ts` 和 HostClient 编排仍较集中 |

这些是工程能力判断，不能用通过的回归数量代替完整动画质量，也不能把 10-21 报告中的“现状”直接搬到今天。

## 3. 尚存差距逐项处理

### G01：Agent 仍在充当工作流脚手架（P0）

**现状**：参考任务和最近缩放试验仍需脚本处理工程登记、引用路径、启动、pin、版本、截图和结果汇总。单次试验已用同一 MCP 会话，不再是全部在 Host 外创作，但这套流程还在验证脚本里。

**方向**：提供稳定的参考创作会话：明确工程、角色、参考、身体/武器范围、sequence/stage 与当前目标；工具根据已实现能力编排准备、候选、查看、修订和保存。保留必要的视觉判断，机械路径与版本由服务处理；只读准备和资产修改分开，沿用原 Writer。

**退出条件**：新 Agent 不读源码、不写临时 JS、不手改 manifest，也能完成“打开已有角色→参考准备→产生一个近似姿态→改一次→看实际图→撤销→保存重开”。先验收这一个任务，随后扩到整段动作。Blender 的价值在于操作持续落到同一实际创作状态。[维护者插件](https://github.com/ahujasid/mcp-for-blender/blob/main/addon.py)

### G02：常用返回仍偏大（P0）

**现状**：已有廉价 digest 和 includeCapabilities:false，但 HostClient.currentFrameState 仍取得整份 state；部分 numeric 包含 visual/顶点，attached 的 metrics resource 也返回完整 state。旧试用 open 约 29.7 万字符是历史样本，不是当前每次都测得的固定大小。

**方向**：公开返回分为摘要、细节、产物三个层次。常用摘要只含完整版本、改动、可用性/失败摘要、下一步和产物引用；完整骨骼/顶点/报告按需读取。内部严格核验继续使用完整数据，不把核验字节全部发给模型。能力用独立指纹，变化时刷新。

**退出条件**：固定同一动作测 tools/list、open、patch、state 的文本字节、图像与模型可见上下文；摘要不遗漏版本和失败，不把输出变小当作已经节约同等比例 token。Blender 的场景查询和 world snapshot 也有精简/有界设计。[源码](https://raw.githubusercontent.com/ahujasid/mcp-for-blender/main/addon.py)

### G03：102 个工具缺少按任务的发现方式（P0，接在 G02 后）

**现状**：schema/角色 capability 已有，tools/list 仍直接返回整张工具表；resources/prompts 不能自动解决工具发现成本。

**方向**：按工程、观察、姿态、参考、动画、审查/导出组织工具目录；常用任务先暴露必要入口与可查的扩展组。客户端支持工具列表变化时再启用动态组；不支持者保留完整列表和任务目录，不能隐藏后又要求调用不存在的工具，也不改为自由执行任意代码。

**退出条件**：实际目标客户端验证“找得到→schema 对得上→能执行”；工具可见性不等于写入权限。Unity 的会话工具组是可借鉴机制。[v10.3.0 manage_tools](https://github.com/CoplayDev/unity-mcp/blob/v10.3.0/Server/src/services/tools/manage_tools.py)

### G04：界面没有突出展示创作判断（P0）

**现状**：数值、截图、视觉/导入已分层，但 Host 主页没有突出参考关系的失败列表、使用了轮廓还是两点估计、当前能否继续编辑。查看五项参考失败仍要读报告或另写展示页。

**方向**：主面板显示当前阶段、观测方法、粗略候选、必要失败和下一步；把“可以继续改”“可以审查”“可以生成正式 motion”“可以提交”分别呈现。固定相机提供参考/当前/前次图，详细技术状态留在展开区。

**退出条件**：同一失败姿态不能只露出“数值通过”；使用者不读 JSON 就知道哪里没对上、还能改什么。Unity 的 advice/staleness 体现了明确就绪状态的方式。[editor_state](https://raw.githubusercontent.com/CoplayDev/unity-mcp/v10.3.0/Server/src/services/resources/editor_state.py)

### G05：失败提示还未形成有效的修正操作（P0）

**现状**：已有结构化错误、remediation、explain_pose 与指标旋钮，并非完全没有建议。但建议与能力未完全对齐：例如 metricAdvice 对 support 提示修改 contact，而附着编辑模式固定支撑、不开放 contact 修改。

**方向**：每个问题给出原因类别、对应部件、当前可用旋钮、允许的修正范围及可执行命令示例。先过滤当前 capability/readiness；区分“标注需要复核”“目标不可达”“缺切片”“数值未收敛”。失败保留可编辑的最佳候选和图，不反复返回一条泛化错误。

**退出条件**：下一步示例在当前会话中可执行，不建议交换身份、改支撑或降低阈值来掩盖失败；修正后能立即回读实际结果。

### G06：动作控制层仍偏底层（P1）

**现状**：body/channels、手脚目标、弯曲分支、附件/层序已有；单臂缩放只完成诊断。仍主要靠坐标和角度拼“收臂、下蹲、低头、起身”，部件相对躯干、可达空间、宽度与末端继承尚未形成角色能力。

**方向**：把常见动作表达为已校准的控制参数，落到同一求解器。补躯干局部方向、角色活动范围，以及受控投影缩短/宽度/手部补偿；参考可靠时拟合，遮挡时采用两点估计。大转身需要实际切片能力，不从单臂缩放虚构背面。

**退出条件**：同一动作意图可在两个角色上使用同一高层入口，输出角色适配后的差异；不能把设置了 scale 参数等同于已经实现透视动作。

### G07：缺少可满足性预检及一致的约束语义（P1）

**现状**：有 IK 与 60 次局部修正，但旧任务的肘角/肩腕距离冲突是在复盘中才被定位；二元关系主要在最后拦截。旧 wrist 指标按自身臂长归一，与新躯干归一指标的职责仍需对齐。

**方向**：迭代前检查长度/目标/弯曲分支的可达范围，区分冲突和求解失败；在硬边界内寻找连续解，不把二元值塞入最小二乘。统一指标的语义、坐标和归一口径，任何规则修订都版本化并保留旧结果。明确用户要严格复刻还是角色适配表达，不由算法自动降低要求。

**退出条件**：已知不相容输入能在大量迭代前说明冲突，并给出实际候选、未满足项和合法调整方向；没有全局证明时不宣称全局无解。

### G08：连续动画编辑还不够顺手（P1）

**现状**：已有 pose→motion、关键姿态、完整候选、GIF、动画/时间选择与审查。当前公共 Host 主要通过 open 选择 animation/time，主页面没有完整时间轴编辑/播放工作流；可以导出 GIF 不等于能顺畅修改某个动作区间。

**方向**：围绕同一 motion 提供阶段和关键帧定位、选中区间调整、播放/暂停/拖动与修改后立即回读。若播放时间与文档版本拆分，需明确新的呈现身份，不能省掉时间/候选绑定来提速。

**退出条件**：修改一个阶段后立即播放或定位验证，能撤销并保持其它阶段。正式组装仍遵循初始准备姿态先通过的规则。Godot 文档明确把轨道/关键帧修改与即时 play/seek 配套。[动画工具说明](https://github.com/satelliteoflove/godot-mcp/blob/main/docs/tools/animation.md)

### G09：角色校准与复用成本仍高（P1）

**现状**：mapping/visualRig、切片关联与审查机制已有，但依赖人工理解角色，缺失关节、不同继承方式和视角经常到制作时才发现。npc1 的成功不能代表其它角色。

**方向**：角色准备流程先列出部件、锚点、切片、继承/约束及视角能力；提供候选、证据图和缺项清单，允许人工修正后复用。自动候选不能自动批准；误差、遮挡和使用的估计方法应可追溯。

**退出条件**：第二个合适的真实角色复用入口，报告校准成本与失败；继续排除用户否定的多拆分皮肤案例。

### G10：新负载的互动速度仍不达预算（P1）

**现状**：固定站姿读取负载曾通过原预算；新单臂缩放两次完整调整约 341/278ms、撤销至图约 259ms，不能写成已满足 120ms，也不应把两次样本报成 P95。

**方向**：先测输入准备、实际求解、比较、发布、序列化、图像各段，再优化最大项。复用已核验静态计算，编辑时返回足够清楚的预览，正式截图按需；批次只做必要求解。不能缓存旧批准/依赖校验来提速，也不默认迁移全部计算到 Host。

**退出条件**：真实角色新负载在同构建/同环境下多轮测原预算；取消、迟到结果、帧版本和源输入仍正确。

### G11：调用、时间、token 与产出质量缺少同口径计量（P1，与 G01/G02 同时设计）

**现状**：已有工具耗时和若干性能证据，参考任务仍靠回合日志复盘；旧的 23/26 次与新 24 次不是同一任务，不能算效率提升。

**方向**：持久任务记录统一 taskId/stageId、阶段耗时、调用数、返回字节、图片/产物和质量结论。模型输入/缓存/输出用量来自客户端实际记录，服务端不能把 JSON 字符数冒充 token。冻结同一参考、角色、起始输入与策略，做 detached/attached A/B，准备成本同口径。

**退出条件**：能回答“这次为什么耗时、哪些调用有效、结果到了哪一步”，不只给总时长或回归数。Aseprite 的工作流 manifest、批次结果与测量说明可借鉴，但其自述收益不作为本项目事实。[工作流与批处理说明](https://github.com/MalloyTheDev/aseprite-mcp)

### G12：研发能力与普通使用路径仍有距离（P1/P2）

**现状**：C2 仍依赖程序内 developmentProfile:'c2-pose'，生产默认 C1 观察；源码、运行服务、便携包与可开放写入范围并不相同。上轮旧 journal 恢复还曾污染试验基线。

**方向**：先交付明确的隔离试用路径，显示程序版本、profile、正在编辑的工程及恢复来源；未保存修改恢复前展示来源和差异，允许明确新建试验/恢复旧会话。连接向导只生成或检测配置，不静默改全局配置。生产限定启用仍遵守原观察/评审条件。

**退出条件**：用户从文档启动后能到达已声明能力；恢复不会被误认为“干净基线”，源码新增不再被误认成旧 exe 已发布。

### G13：缺少完整、可再次编辑并经真实导入的作品（P1/P2，导入环境可提前核对）

**现状**：有完整工程链路及机械回归，尚没有本次 GIF 的完整合格动作，也缺第二角色、独立 Spine 导入和充分长期使用证据。

**方向**：选一个适合当前切片能力的完整动作，按阶段产出候选、参考/实际图、原速动画、审查报告与可编辑源；最后在目标版本 Spine 独立副本导入。导入工具/版本可提前探测，但本轮未执行该步骤。

**退出条件**：形成可重开修改的真实完整作品，并记录未匹配部分；CLI/runtime 可加载不能替代 Spine 编辑器导入。

### G14：维护与回归仍需围绕真实使用收敛（P2，随各项施工）

**现状**：已有共享内核和较多协议/故障测试，但注册、宽泛参数准备与模式路由仍集中在 server.ts，HostClient/Store 的职责也在增长；fixture 通过不能覆盖真实画面与动作质量。

**方向**：按领域集中维护 schema、handler、capability、错误、返回摘要和文档映射；保留相同内核，逐步拆适配器，不重写已验证事务。机械、协议、真实截图、动作视觉、导入与长期使用各自记录，避免新增测试只是在断言实现细节。

**退出条件**：新增一个受控动作不需要在多处手工重复定义相同参数；工具声明与实际行为、文档、回放及新鲜度回归一致。

## 4. 建议的收尾顺序

1. **先交付能持续使用的一小段工作流**：G01、G02、G04、G05。用户给参考，Agent 在 Host 中产出近似姿态、修改、看图、撤销、保存；接口返回简洁且可操作。G11 的任务记录同时埋入，工具分组 G03 紧随其后。
2. **再增强动作表达与求解**：G06、G07、G09，使粗略候选更接近目标，解决已发现的表达边界；同时测 G10，避免后期才发现交互变慢。
3. **形成完整动作与日常使用版本**：G08、G12、G13，以真实作品和可重开使用验收；G14 随改动逐步收敛。导入环境检查可提前并行于其它人工工作，但不另开 Agent 或任务。

最小下一批应围绕“一个参考姿态在一个持续会话中可改、可看、可撤销、可重开”验收。当前缺口主要集中在这套创作操作能否顺畅组合，而不是继续增加工具数量或扩大到通用 3D 编辑器。既有 Writer/版本/备份保持，未知内容明确标注；失败也应有当前最佳候选、证据和可执行下一步。
