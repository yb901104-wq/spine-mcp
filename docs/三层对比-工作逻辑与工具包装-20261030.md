# 同类 MCP 逐层对比：工作逻辑、步骤大类与工具包装

日期：2026-10-30
对比对象：

| 简称 | 项目 | 一句话定位 |
|---|---|---|
| **我们** | `D:/AI_cc/spine-mcp`（spine-json-mcp） | 以**磁盘 JSON 为真值**的 Spine 动画编辑 MCP，无宿主也能跑 |
| **S** | `zhoushengmin/spine-mcp-server` | 以 **Spine 编辑器 CLI 为真值**的 `.spine` 往返编辑 MCP |
| **B** | Blender MCP（addon + socket） | 以 **Blender 进程内存为真值**的 3D 建模 MCP |
| **U** | Unity MCP（Bridge + Relay/Python） | 以 **Unity Editor 进程内存为真值**的引擎 MCP |
| **F** | Figma MCP（官方云服务） | 以 **Figma 云端文件为真值**，主要做"设计 → 代码"的 MCP |

本文回答四个问题：**① 完成工作的逻辑是否一致 ② 步骤大类是否一致 ③ 同为 MCP，给大模型的"工具包装"差在哪 ④ 逐层结构对照**。

---

## 0. 先给结论（三句话）

1. **步骤大类高度一致**——五个项目都是"勘察 → 准备/绑定 → 生成草案 → 验证 → 审查 → 写入 → 回读复核"这七步，只是每步的"严格程度"差一个数量级。
2. **工作逻辑的"真值观"完全不同**——这是所有差异的**根因**：S 的真值在磁盘上的 `.spine` 二进制（由官方 CLI 读写，见 §1.5/§1.6 更正：**它并不持有常驻宿主**）、B/U 的真值在宿主进程内存、F 的真值在云端、我们的真值在磁盘 JSON。真值在哪，决定了"写入"这一步怎么做、能不能撤销、断线了还能不能用。
3. **工具包装的差别不在数量，在"返回体里塞什么"**——我们往返回体里塞的是**流程凭据**（版本四元组 / 审查令牌 / 期望哈希 / 逐项检查），别家塞的是**内容**或**句柄**。这是"工具集"与"带门禁的工作流"的分界线。

## 1. 第一层：真值在哪（决定一切的根因）

| 项目 | 真值存放地 | 宿主必须活着吗 | 断线/无授权时会怎样 | 撤销靠什么 |
|---|---|---|---|---|
| 我们 | **磁盘 JSON 文件**（`resolveWorkspacePath` 限制在工作区内） | **不需要**（Host 是可选加速层，detached 模式下 MCP 自维护 activeDoc 镜像） | 照常工作，只是少了实时画布与内存会话 | journal + undo/redo + 备份 + `spine_restore` |
| S | **`.spine` 二进制**（Spine Pro CLI 3.8.75 导出/导入） | **必须**（要装 Spine Pro 授权 + CLI 路径） | **完全不可用**（`configManager.assertSpineExists()` 直接失败） | `.bak` 备份 + `spine_rollback` |
| B | **Blender 进程内存**（addon 起 TCP 9876） | **必须**（Blender 开着、面板点 Start） | 工具全失败，且未 `save_file` 的改动**随进程消失** | Blender 自己的 undo / `undo` 工具 |
| U | **Unity Editor 进程内存**（Bridge + Relay IPC） | **必须**（Editor 启动自动拉起 Bridge） | 同上；`manage_editor` 有 undo/redo，但内存态丢失即丢失 | Unity Undo 栈 + `manage_editor` |
| F | **Figma 云端文件**（官方远程 `https://mcp.figma.com/mcp`） | 不需要本地应用，但**要联网 + OAuth 席位** | 超出席位限额（Starter 6 次/月）直接停 | Figma 自己的历史版本 |

**通俗版**：
- S/B/U 是"**我要借用别人的编辑器，改完得还回去**"——所以它们天然需要一个活着的应用，好处是能吃掉编辑器的全部能力，坏处是断了就废、且改的是别人内存里的东西。
- F 是"**我去云端读设计稿，代码我自己生成**"——所以它几乎不改真值（写入仍标 beta）。
- 我们是"**文件就在我自己的地盘，我直接改文件，改完自己验**"——好处是不依赖商业软件和常驻进程，代价是**所有"编辑器帮我兜底"的能力都得自己实现**（求解、回读、规范校验、视觉比对）。

## 1.5 更正与补论：S 依赖的不是"宿主"，是"官方命令行批处理"

> ⚠️ 前稿把 S 描述为"编辑器在环的宿主"，**用词不准**，本节更正。它在结构上**没有宿主**。

### 1.5.1 "闭源"不等于"没有接口"

Spine 是闭源商业软件没错，但 Esoteric Software **官方文档公开提供了一整套命令行接口**（Command line interface，见 <https://en.esotericsoftware.com/spine-command-line-interface>）。这不是破解、不是逆向、不是内存注入，是官方写进用户手册的正门。

Windows 安装包里本来就有**两个**可执行文件，官方的说法是：

| 可执行文件 | 是什么 | 行为 |
|---|---|---|
| `Spine.exe` | GUI 应用 | 启动后**不弹 console、不等待退出** |
| `Spine.com` | 命令行应用（Windows 传统，不带扩展名输入 `Spine` 时优先执行它） | 输出重定向到 console，**并阻塞等待 Spine 退出** |

> 官方原文：「The COM file is a command line application, it directs Spine's output to a console window and **waits for Spine to exit**.」——所以 `Spine.com` 才是 CLI 调用的正确目标。S 的 `constants.ts:9` 写死 `SPINE_EXE_NAME = "Spine.com"`，正是对着这条来的。

### 1.5.2 决定性的一句话：它跑完就退出

官方使用说明开头：

> 「When run in this way, Spine starts, does one or more exports or texture packings, then **exits**」

所以 S 的每一次工具调用，实际是这样的一件事：

```
spawn("D:/…/Spine.com", ["-i", json, "-o", project, "-r", name])
   → 启动一个 JVM 进程（Spine 是 Java 程序，-Xmx2048m 是 JVM 参数，默认最大堆 2048MB）
   → 干活
   → 进程退出
```

`src/spine/cli-executor.ts:48` 就是这一行 spawn。它不是常驻宿主，**是每调一次就开机一次的批处理**。

S 用到的参数与官方手册**逐字对应**：

| S 代码里的调用 | 官方手册里的原型 / 示例 |
|---|---|
| `["-i", jsonPath, "-o", projectPath, "-r", skeletonName]`（import-service.ts:62） | `Spine -i <path> [-s <scale>] -o <path> -r [<name>]`；官方示例 `Spine -i /path/to/skeleton.json -o /path/to/project.spine -r skeletonName` |
| `["-i", filePath]`（version-validator.ts:80，取版本） | Info：`Spine -i <path>` |

结论：**S 没有把 Spine 变成宿主，它把 Spine 当成一台 `ffmpeg` / `gcc` 那样的命令行编译器来用。**

### 1.5.3 三种集成面（这次按"能不能摸到内存"来分）

前稿按"真值在哪"分层是对的，但更底层的分野是**集成面**——你站在这程序的哪个位置跟它说话：

| | **A. 进程外 · 批处理 CLI** | **B. 进程内 · 常驻插件 + Socket** | **C. 无宿主 · 自带引擎** |
|---|---|---|---|
| 代表 | **S（spine-mcp-server）** | Blender MCP / Unity MCP | **我们** |
| 怎么说话 |  spawn 子进程，传 argv | 在宿主里装插件，插件起 TCP/IPC 常驻服务 | 自己引 runtime 库，在自家进程里算 |
| 拿得到什么 | **stdout 文本 + 退出码 + 磁盘产物** | **内存里的活对象** | **自家内存里的对象** |
| 宿主死了 | 下一次调用会失败 | 全部工具失效，未保存改动随之蒸发 | 无影响，照常跑 |
| 有没有会话 | **没有**（进程每次都退出，状态只能落磁盘） | **有**（宿主进程天然就是会话） | **有**（我们自建 activeDoc / journal / undo） |
| 单次调用开销 | **秒级**（起 JVM + 加载项目） | 毫秒级 | 毫秒级 |

### 1.5.4 这一条更正，反而解释了前稿的两个疑点

| 前稿的观察 | 现在的原因清楚了 |
|---|---|
| S 全仓 grep **命中 0**：`dryRun` / `expectedHash` / `reviewToken` / `writer` / `lock` / `undo` / `journal` | 它每次调用的进程**都是新进程**，内存中没有任何东西可串行化，也没有第二个 writers 可以竞争。唯一跨调用存活的是磁盘文件，所以它的保护只能到 `.bak` + `spine_rollback` 这一层。 |
| S 是五级项目里**唯一没有会话状态**的 | 同一个原因：批处理进程天然没有会话。它的**广度**（70 个工具横跨七个域）是用**放弃纵向状态**换来的。 |

### 1.5.5 这条路的真实代价（决定了我们不走它）

| 代价 | 依据 |
|---|---|
| **必须买 Pro 授权（$379 一次性）** | Essential（$69）官方明确：**不导入网格附件与约束**，且不能保存/导出含 mesh、IK 的项目。S 的 README 直接写 "requires Spine 3.8.75 **Professional**"。 |
| **并行被许可证封顶** | 官方：Essential/Pro 为**单一具名用户**，激活码最多装两台计算机，且「**同一时间只有一台在使用**」。CI 并发跑 2 个任务就会撞上。 |
| **版本被锁死在 3.8.75** | S 的 `SUPPORTED_SPINE_VERSION = "3.8.75"`；它 `config-manager.ts` 里默认搜索路径甚至是作者本机的 `D:/cocos/SpinePro3.8.75/Spine.com`。换版本要重装、重认缴出资校验。 |
| **headless 有例外** | 官方：「导出**图片或视频**需要 OS 窗口系统与 OpenGL」。所以它的 `render_preview`、`export_video` 在无图形环境的机器上不成立——这一点在它的 README 里没有显著标注。 |
| **拿的不是结构化数据，是屏幕文本** | `version-validator.ts:39` 用正则 `/Spine version:\s*([0-9]+\.[0-9]+\.[0-9]+)/i` 从 stdout 里**刮**版本号；出错时只能拿到 `stderr.slice(0,500)`。集成面就是文本 + 退出码，官方版本改一下输出格式就会断。 |
| **秒级延迟** | 每次工具调用=启一次 JVM + 加载项目。它因此专门加了 60s 超时保护（`cli-executor.ts:68`）和 `CLI_TIMEOUT_MS` 配置。 |

### 1.5.6 反过来这才看清楚：我们俩正好互补

```
                  编辑器权威（官方引擎兜底）
                            ▲
                            │
   S 有这一层 ✔             │              S ✘ 没有这一层
   （改完能问 Spine 吃不吃得进）│              （批处理进程天然无会话）
                            │
   ─────────────────────────┼─────────────────────────
                            │
   我们 ✘ 没有这一层          │              我们有这一层 ✔
   （不装商业编辑器）          │              （activeDoc / 版本四元组 / journal / undo / pin）
                            │
                            ▼
                  会话状态（能否多步迭代后一次提交）
```

- **S 的广度来自"借力"**：它不用自己实现 mesh、皮肤、约束、图集，Spine 编辑器替它做，所以它能开出 70 个工具横跨七个域。
- **S 的浅处也来自"借力"**：集成面只有 argv + stdout，它就**没法**做我们这种"先反复调整、最后一次性落盘"的模型——因为每次调整都是一次完整的应用启停。
- **我们恰好相反**：没有编辑器权威，所以只能把能力做窄（V1 只碰动画时间线），但换来的是毫秒级迭代、完整会话、可撤销、可离线。

这也顺带说明：`docs/plans/host-evolution.md` 里我们要造的那个常驻宿主，补的**正是 S 结构上拿不到的那一层（会话状态）**，而不是去复刻它的（编辑器权威）。两条线不是竞争关系，是各自补齐自己的短板。

## 1.6 破除一个误解：官方 CLI **不提供**任何动画编辑命令

一个很自然的推测是：既然 S 能调官方渠道，那它的动画能力是不是"白嫖"来的，而我们要自己分析 JSON 规则、手写每一条 MCP 动作？

**推测不成立。** 实测结果正好相反。

### 1.6.1 S 用到的全部 CLI 参数只有六个

对 `src/spine/` 全量 grep 实际传入的参数：

```
-e   --export     -i   --input      -l   --logout
-m   --clean      -o   --output     -r   --import
```

对照官方文档，这六个参数能做的事是 **export / import / cleanup / logout / info** ——全部是**文件级**操作（把项目导成 JSON、把 JSON 导回项目、动画清理、打包图集）。

官方 CLI 参数表里**不存在**"设置骨骼旋转""添加关键帧""修改插槽颜色""创建动画"这类命令。**这类能力在 CLI 里开口都没有。**

### 1.6.2 中间的"改动画"，和我们是一模一样的手撸 JSON

S 修改动画的真实链路（`src/spine/modify-service.ts:29`）：

```ts
export async function modifyProject(
  projectPath: string,
  modifyFn: (json: any) => void,   // ← 注释原文：「接收解析后的 JSON 对象，直接原地修改」
  ...
)
```

而 `json-handler.ts` 的开篇注释，是**手写的动画时间轴结构说明**：

```
Spine 3.8 动画时间轴结构：
   animations.<name>.bones.<boneName>.rotate[]     每帧 { time, angle }
   animations.<name>.bones.<boneName>.translate[]  每帧 { time, x, y }
   animations.<name>.bones.<boneName>.scale[]      每帧 { time, x, y }
   animations.<name>.bones.<boneName>.shear[]      每帧 { time, x, y }
   animations.<name>.slots.<slotName>.attachment[] 每帧 { time, name }
   animations.<name>.slots.<slotName>.color[]      每帧 { time, color }
```

**这段和我们 `src/policies/`、`src/官方JSON规范审查` 里维护的结构知识是同一种东西。** 它不是从官方 API 拿来的，是作者读 JSON 结构总结出来的。

### 1.6.3 量化：它 89% 的领域代码和我们是同一种工作

按"是否依赖 `cliExecutor`"给 `src/spine/*.ts` 分类（共 30 个文件）：

| 类别 | 文件数 | 行数 | 占比 |
|---|---|---|---|
| **纯 JSON 操作**（自己分析结构、自己撸规则） | 24 | **4,831** | **≈89%** |
| **调用官方 CLI**（含 `cli-executor.ts` 封装层自身） | 6 | **577** | **≈11%** |

纯 JSON 侧的大头：`json-handler.ts` **1234 行 / 44 个导出函数**、`render-service.ts` 533、`animation-generate-service.ts` 307、`assemble-service.ts` 216、`split-atlas-service.ts` 213、`cut-parts-service.ts` 172、`effect-service.ts` 181。

**结论：S 的 70 个工具不是"官方命令的薄包装"，绝大多数也是自己一格一格手撸出来的 JSON 变换。** 它和我们一样，要自己分析 JSON、自己实现规则、自己包装 MCP 工具。

### 1.6.4 那么真正的差距只有一条

不是"能不能用官方命令"，而是——

> **写完之后，谁来判断这个 JSON 格式对不对？**

| | 裁判是谁 | 代价 |
|---|---|---|
| **S** | **外包给官方 Spine 导入器**：改完丢进 `Spine.com -i ... -r`，Spine 认不认它说了算 | $379 Pro 授权 + 锁版本 3.8.75 + 秒级 + 无会话 + 许可证限制并发 |
| **我们** | **自己实现裁判**：`docs/官方JSON规范审查.md` 描述的规范审查层 + 官方 runtime 回读 | 免费、全版本、可离线、有会话；但规则要自己维护，且不等于官方导入器的全部判定 |

我们 AGENTS.md 里"官方 JSON 规范审查必须覆盖 Spine 导入器敏感规则（例如 `curve` 只描述当前关键帧到下一关键帧的插值，timeline 最后一帧不能包含 `curve`）"——**这一整层就是在人工复刻 S 白嫖到的那个裁判。**

### 1.6.5 由此得到三条判断

1. **"我们的工作量大是因为绕路"——不成立。** 同样的结构分析与规则实现，两家都得做，比例上 S 甚至更多（它还要额外维护 Round-Trip、临时目录、`.bak` 与让导入器满意的兼容性）。
2. **真正可以讨论的只有一件事**：要不要把"编辑器兼容性确认"也接进来。建议是**接，但只做默认关闭的 advisory 终验**（见 §6 借鉴第 1 条）——用来回答"这个文件 Spine 编辑器能不能打开"，**不进主链路、不放宽任何现有门禁**。因为一旦进主链路，我们就要为它付出上面那张表的全部代价，换来的却是一张现在已经有的门票性质相同、但更贵的证明。
3. **我们多出来的两样东西，S 结构上拿不到**：毫秒级会话内迭代（上面 §1.5.3 的由来）与框架内的视觉回传。这两样才决定 Agent 能不能"一边看一边改"。

## 2. 第二层：完成一件事的"步骤大类"是否一致

### 2.1 共同的九步骨架

五个项目各自的标准作业流程，抽象出来是同一张骨架：

```
① 发现/勘察 → ② 准备/校准/绑定 → ③ 生成草案 → ④ 求解/计算 → ⑤ 验证(数值)
→ ⑥ 审查(视觉/人工) → ⑦ 写入/提交 → ⑧ 回读复核 → ⑨ 导出/交付/回滚
```

### 2.2 逐格对照（✔=有专门工具/机制，△=部分或靠人工，✘=没有）

| 步骤 | 我们 | S | B | U | F |
|---|---|---|---|---|---|
| ① 发现/勘察 | ✔ `spine_get_document_summary` / `spine_inspect_character` / `spine_get_workspace_tree` / `spine://session` 资源 | ✔ `spine_check_project`（版本/atlas/引用完整性/骨骼角色覆盖率）+ `spine_describe`（骨骼树+角色建议） | ✔ `get_scene_info` / `list_objects` | ✔ `scene-list-opened` / `gameobject-find` | ✔ `get_metadata`（**轻量 XML 骨架**）+ `whoami` |
| ② 准备/校准/绑定 | ✔ mapping 四态生命周期 `draft→validated→calibrated→confirmed`；`spine_calibrate_visual_rig`、`spine_calibrate_arm_perspective` | △ 靠 `spine_describe` 的角色建议 + 人工确认（无生命周期状态机） | △ 无（直接对对象操作） | △ 无（直接对 GameObject 操作） | ✔ `get_code_connect_map`（设计组件 ↔ 代码组件映射） |
| ③ 生成草案 | ✔ `spine_create_pose_draft` / `spine_create_reference_pose` / `spine_build_motion_from_poses` | ✔ `spine_assemble` / `spine_generate_animation`（sine/bob 模板）/ `spine_cut_parts` | ✔ `create_primitive` / `create_mesh` | ✔ `gameobject-create` / `create_script` | ✔ `generate_figma_design`（网页→图层） |
| ④ 求解/计算 | ✔ **`spine_solve_pose`**（官方 runtime 求解 + IK 可达性 + 膝部屈曲） | ✘ 无求解器（改数值即结果，靠编辑器导入时计算） | △ Blender 自己算（修改器/物理） | △ Unity 自己算 | ✘ 不适用 |
| ⑤ 验证（数值） | ✔ `spine_validate_spine_json` / `spine_validate_mapping` / `spine_validate_motion` / `spine_compare_pose_graphs` / `spine_run_validation_pipeline` | ✔ **round-trip 重导出比对**（rotation 误差 <1e-6）+ 引用完整性（悬空骨骼/插槽/约束 target） | △ `get_object_info` 回读 | ✔ `validate_scripts` / `tests-run` | ✔ `get_variable_defs` / 截图比对 |
| ⑥ 审查（视觉/人工） | ✔ **`spine_review_pose` / `spine_review_animation`**：必须带 `playerManifestPath` + 五项独立 `checkResults`（每项 status+reason），产出 `reviewToken` | △ 有 `spine_render_preview`，但**没有"批准"这一步** | ✔ `screenshot-*` 系列 + 模型自己看图 | ✔ `screenshot-camera/game-view/scene-view` | ✔ `get_screenshot` 作为视觉基线 |
| ⑦ 写入/提交 | ✔ **`dryRun` 默认 true**；真写入需同一输入 + `expectedHash` + `reviewToken`；Host 侧还要 `expectedRevision`（版本四元组）与强制 pin | ✔ 直接写；写入前自动 `.bak` | ✔ 直接写（改内存）；落盘要 `save_file` | ✔ 直接写（改内存）；落盘要 `scene-save` | △ `use_figma` 写入，**标 beta**，且 Figma 要求先加载 14 个 Agent Skills |
| ⑧ 回读复核 | ✔ 官方 runtime 回读 + `spine_recheck_pose` + `spine_get_pose_state` + 参考关系比较 v4 + 黄金帧 | ✔ **导入后重新导出比对关键帧**（这是它最强的点） | △ `get_object_info` | △ `object-get-data` | ✔ 截图比对（Playwright 视觉门） |
| ⑨ 导出/交付/回滚 | ✔ `spine_export_*` / `spine_render_animation_gif` / `spine_list_backups` / `spine_restore` / `spine_rollback` | ✔ GIF / 精灵表 / video 导出 + `spine_rollback` | ✔ `render_image` / `export_scene`(FBX/OBJ/GLTF/USD) | ✔ `manage_build` | ✔ `download_assets`（导出原图/切图） |

### 2.3 步骤大类的判定

**是一致的**：①②③⑦⑨ 五步，五家都有，只是名字不同。

**不一致的地方集中在 ④⑤⑥⑧ 这"中间四步"**——也就是**"改完之后、交付之前"的验证地带**：

| 差异 | 我们 | S | B/U | F |
|---|---|---|---|---|
| 有没有"求解"这一步 | 有独立求解器 | 无（靠编辑器） | 宿主代劳 | 不适用 |
| 验证是"数值"还是"所见即所得" | 数值 + 视觉**双轨且互相不顶替** | 数值（重导出比对） | 视觉（截图）为主 | 视觉（截图比对）为主 |
| 有没有"批准"这个显式动作 | **有**（`spine_review_*` 产出令牌） | 无 | 无（改了就是改了） | 无（写入是 beta） |
| 写入后是否强制回读 | **是** | 是（round-trip） | 否 | 否 |

## 3. 第三层：同为 MCP，"工具包装"差在哪

这一层是**给用户（大模型）看的东西**：工具怎么定义、怎么校验、返回什么、出错说什么。

### 3.1 包装逻辑（代码层面）

| 维度 | 我们（`src/server.ts` + `toolCatalog.ts` + `toolError.ts`） | S（`BaseTool` + zod） | B/U | F |
|---|---|---|---|---|
| 工具定义方式 | 大数组 + 若干 `xxxToolDefinitions` 拼装，最后统一后处理 | 一文件一工具类，继承 `BaseTool`，`discover_modules()` 扫描目录 | 装饰器/特性自动注册（`@mcp_for_unity_tool` / `[AiTool]`） | 官方闭源，工具即 API |
| 工具数量 | **约 115**（静态清点 `src` 内 `spine_*` 标识 116 个） | 70（71 个 tool 文件） | B 27–36；U 36–71 | 约 30（读 13 / 写 10+） |
| 入参校验 | **Ajv 强校验**，启动即为每个工具建 validator；`additionalProperties:false`；`required` 缺声明直接启动报错 | zod `inputSchema`，靠各工具自己 `parse` | 宿主侧按 action 分派自校验 | 服务端校验 |
| 统一注入字段 | **每个工具自动补 `responseDetail:summary|full` 和 `projectId`**（`server.ts` 尾部 for 循环） | 无 | 无 | 无 |
| 工具可见性管理 | **8 个工具组**（project/observe/reference/pose/animation/review/workflow/discovery）；动态模式下默认只开 4 个 core 组；`spine_get_tool_catalog` 查询；`nextAction` 指向未启用工具时**自动替换为目录查询指令** | 无（全量暴露） | U 有 Project Settings 逐个 enable/disable | 无 |

| 图片回传 | **有**：`pickImages()` 把渲染页 PNG 转 base64 `image` 内容块（≤3 张），避免"只给路径让人自己去看" | 无 | B/U 有截图工具（单独调用） | 有 `get_screenshot` |
| 进度 / 取消 | **有**：`progressToken` → `notifications/progress`；`AbortSignal` + `runTask/checkpoint` | 无 | U 有异步命令框架 | 无 |
| 遥测 | **有**：`recordCreationCall` 记录 durationMs / textBytes / images / error，落盘失败也不影响回执 | 无 | 无 | 无 |
| 逃生口 | **没有** `execute_*` 任意代码口（只有 op 白名单） | 无 | **有**：`execute_python` / `execute_code` / `execute_menu_item`（B 有 `BLENDER_MCP_SAFE_MODE` 校验拦截） | 无 |

### 3.2 包装"内容"：返回体里到底塞了什么（最关键的一节）

这是我们认为最值得记住的一条对照：

| 项目 | 返回体的主角 | 通俗说法 | 模型拿到后要做什么 |
|---|---|---|---|
| **F** | **内容**：一整段 React + Tailwind 代码、XML 结构、截图 | "我把设计稿翻译好了，你直接改这份代码" | 直接生成/修改代码 |
| **B / U** | **句柄**：`{status, message, objectName}` | "我改完了，给你个名字，后面你自己拼" | 自己记住对象名，继续调别的工具 |
| **S** | **结果 + 建议**：`{success, message, errorCode, data:{suggestion}}` | "我做完了/没做成，建议你下一步这样" | 按 suggestion 走 |
| **我们** | **状态机凭据 + 逐项检查**：`version{sessionId,documentId,openEpoch,revision}`、`reviewToken`(64 hex)、`expectedHash`、`checkResults{每项status+reason}`、`nextAction{tool,instruction}`、`issues` | "我给你一张**通行证**，你下次调用必须带上，否则我拒收" | **必须带凭据进入下一步** |

**这就是本质差异**：
- 别家的工具是**"动作"**（调一次，做完就完）。
- 我们的工具是**"流程节点"**（调一次，拿到进入下一节点的凭据；凭据不对/过期/缺项，直接 `REVISION_CONFLICT` / `REVIEW_REQUIRED` / `TARGET_STALE` 拒收）。

代价也很实在：**我们每多一道凭据，就多一次调用、多一份 token、多一个模型可能填错的字段**。这也是为什么我们有 `spine_get_tool_catalog` 做动态裁剪、`responseDetail:summary` 做默认摘要——是为了给这套重流程减负。

### 3.3 一个具体对照：同一个"写"动作，四家的入参

| 项目 | 写入工具 | 入参长什么样 |
|---|---|---|
| S | `spine_set_bone` | `{projectPath, boneName, x, y, rotation, ...}` —— 直接改，写完自动 `.bak` |
| B | `create_object` | `{type:'cube', location:[..], scale:[..]}` —— 直接改内存 |
| U | `manage_gameobject` | `{action:'create', name, ...}` —— **一个工具 + action 分派**（36 个工具覆盖上百个动作） |
| **我们** | `spine_retarget_motion` | `{motionPath, outputMotionPath, dryRun:true}` 先预演 → 拿到 `diff`/`reviewToken` → **同一输入 + `expectedHash` + `reviewToken` + `dryRun:false`** 才真写；attached 模式还要 `expectedRevision` 四元组 |

顺带一提 **U 的 "大工具 + action"** 与我们的 **"一动作一工具"** 是两个极端：
- U：`manage_graphics` 一个工具 33 个 action、`manage_physics` 21 个 action → 工具少（36），但**单个工具的 schema 巨大**，模型容易传错 action。
- 我们：`spine_set_pose_target` / `spine_set_pose_channel` / `spine_batch_pose_ops` 拆开 → 工具多（115），但**每个 schema 小而确定**，且能精确裁剪可见性。
- S 走中间：70 个工具，颗粒度接近"一个骨骼操作一个工具"。

## 5. 直接回答："我们的工作逻辑和它一致吗？"

### 一致的（4 条）
1. **大循环一致**：读 → 改 → 验 → 写 → 复核，骨架相同。
2. **"先给模型看清现场，再让它动手"一致**：它的 `check_project`/`describe`，我们的 `spine_inspect_character`/`spine_get_tool_catalog`/`spine://session`，都是先发地图。
3. **"写之前先算一遍"一致**：它的 round-trip 重导出比对、我们的 `dryRun` + 官方 runtime 回读，目标都是"证明写进去的和我算的是一回事"。
4. **"图片要给模型看"一致**：它有 `spine_render_preview`，我们有 `pickImages()` 直接回传 PNG base64。

### 不一致的（4 条，且都是我们刻意选的）
1. **真值位置**：它认编辑器，我们认文件 → 导致它能覆盖更广（皮肤/网格/图集/约束都能改），我们只做动画时间线这一件事但做得深。
2. **写入是否要凭据**：它写完即成（有 `.bak` 兜底），我们写完还要过"审查令牌 + 期望哈希 + 版本四元组"三道。
3. **是否允许推断**：它 `sideOf()` 用**末位数字奇偶**判左右、默认给所有非末帧写 ease curve；我们**明令禁止**按名字/序号推断解剖身份，无曲线证据不写 curve。
4. **是否有逃生口**：B/U 有 `execute_python`/`execute_code`，我们**没有**，改东西只能走 op 白名单。

## 6. 值得借鉴（按性价比排序，只增不改）

1. **错误码补 `suggestion`**（成本最低、收益最直接）——它的 `suggestion` 是"下一步具体做什么"。我们 `toolError.ts` 已有 `remedies` 表但只覆盖 6 个码，建议补齐 `TARGET_NOT_PINNED`、`REVIEW_REQUIRED`、`TARGET_STALE`、`NO_SOLUTION`、`CONTROL_REQUIRED`、`DOC_INCOMPLETE`。
2. **Round-Trip 作为可选终验**（我们已有 L2 待办里的同类想法）——做成**显式、advisory、默认关闭**的收尾动作：把当前产物导入一次、重导出、比对关键帧数值，落证据（哈希/版本/耗时/原始输出）。**不替代、不放宽**现有三层视觉验证。
3. **地图式只读入口**——把现在分散在 mapping 校准、pose 流程、准备姿态门禁、C2 资产前置里的"能不能开工"判断，收敛成一个只读 `spine_project_brief`：覆盖率 + 阻塞原因列表 + 建议下一步，**不授予任何权限**。
4. **"AI 出显式索引 → 程序确定性装配"两阶段切分**（`cut_parts → assemble`）——和我们"启发式只出候选、装配必须有显式依据"的原则同构，将来做图集/部件可照此形态。
5. 次要：精灵表/video 导出形态、一键安装自检、按能力域给测试打标签。

### 明确不借鉴（5 条）
- 按名字/序号**推断**解剖身份（左右/前后）。
- **默认**写 ease curve。
- 无 dryRun / 无审批 / 无写者锁的**直接覆盖写入**。
- 用 `copyFileSync` 冒充原子替换（中断会半写）。
- 引入 `execute_*` 任意代码逃生口（B/U 有，我们不做）。
