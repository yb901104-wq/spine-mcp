## C1 前一轮异步路径核验复验（2026-10-23）

Host 的逐次依赖核对、MCP 快照依赖检查与 journal 读取使用原生异步 lstat/realpath 调度。同步及异步入口共用词法工作区边界；每个文件仍重新核验真实根及最近现存祖先，断开的链接不能当作未创建文件越过检查。检查器最多并发 8 个文件，journal 最多每批 4 个，解析失败也等待其它读取收束，不缓存路径结论、size/mtime 或 SHA-256 门禁结果。

journal 先完成路径解析再处理文件读取的 ENOENT，避免把断链解析失败吞成空 journal。新增现存/未创建路径、junction 改指根外、断链、同 size/mtime 字节变化及异步失败收束回归；同步写入路径、完整版本、授权、备份、官方 JSON 审查、diff 白名单和视觉门禁均未放宽。

## Host 事务读取与页面刷新收尾（2026-10-23）

journal 枚举按最多四个文件一批严格读取，全部 settle 后按原枚举顺序消费；每次重新读取并验证 checksum 链，不复用上轮校验。索引与 requestId 查询沿用相同规则，跨批查找、篡改拒绝及恢复后重新核验有独立回归。

同一次 Host 操作入口核对实例身份后，编辑/撤销末尾依次读取状态与 PNG，避免严格文件读取与栅格计算竞争；交叉核对二者完整 VersionRef，任何失败或不一致都不返回混合版本结果。提交的只读候选与快照可并发，失败先收束其它读取；快照携带当前 reviewHash，候选与快照均须匹配预期完整版本。授权、备份、journal、原子发布及最终严格检查仍顺序执行，审查变化仍使旧授权失效。旧 Host 缺少 reviewHash 时明确版本不匹配，不将缺项当 null。

浏览器仅合并重复状态刷新和同版本已显示图片，严格 state 查询不缓存；完整版本/derived/依赖指纹变化或手动刷新会重新取图，stale 不能借已显示图片通过校验。这不是服务端门禁缓存或截图证据复用。页面仍无写入权限。

## 推荐流程

对于 v2 语义动作，真实写入前还必须完成：

- `spine_create_mapping_draft` → `spine_validate_mapping` → `spine_calibrate_mapping` → `spine_confirm_mapping`。
- 参考动画先通过 `spine_extract_motion` 生成 v2 motion，再调用 `spine_validate_motion`。
- `spine_retarget_motion` dryRun 必须返回 `ok:true` 和 `reviewToken`；提交时必须复用该 token、dryRun 返回的 `expectedHash` 和相同输入。
- 如果 mapping 状态不是 `confirmed`、校准报告 hash 不匹配、IK 不可达或脚底/手腕/闭合误差超阈值，工具不得写入。

1. **读取摘要**
   - 调用 `spine_get_document_summary`。
   - 记录 `hash`、版本和可写状态。

2. **分析目标**
   - 调用 `spine_get_animations`、`spine_get_animation_sheet` 或相关读取工具。
   - 确认目标动画、骨骼、插槽和时间范围存在。
   - 如果要从自然语言生成一整段新动画，优先规划为 `spine_apply_pose_sequence` 的 `poses`，避免拆成多次单点写入。

3. **先 dryRun**
   - 调用写工具时保持 `dryRun:true`。
   - 传入 `expectedHash`。
   - 检查返回的 `summary`、`diff`、`operationValidation` 和 `officialSpecValidation`。

4. **校验**
   - 调用 `spine_validate_json`。
   - 确认结构和引用关系仍然通过。

5. **确认后提交**
   - 对同一文件或副本文件再次调用写工具。
   - 设置 `dryRun:false`。
   - 继续传入最新 `expectedHash`。
   - 工具会自动在 `backups/` 生成备份。

6. **提交后复查**
   - 再次调用 `spine_get_document_summary`。
   - 优先调用 `spine_run_validation_pipeline`，一次性确认结构校验、官方 runtime 加载验证和浏览器预览入口。
   - 如果没有 atlas 或暂时不需要预览，再单独调用 `spine_validate_json`。
   - 检查 `hashAfter`、`backupPath`、`summary.wroteFile`。

7. **人工预览确认**
   - 打开 `spine_run_validation_pipeline` 返回的 `previewUrl.url`。
   - 确认动画能播放、切片显示正常、动作观感符合预期。

## 导入失败恢复流程

如果 Spine 软件真实导入失败，或发现写入后的 JSON 存在未被 MCP 捕获的规范问题，必须按以下流程处理：

1. 停止继续在当前错误 JSON 上叠加修补。
2. 调用 `spine_list_backups`，按目标 `filePath` 列出候选备份。
3. 选择最近一次确认可导入或写入前的备份，先调用 `spine_restore_backup` 且保持 `dryRun:true`。
4. 检查 dryRun 返回的 `restoreSourceHash`、`validation.ok` 和目标文件当前 hash。
5. 确认无误后再次调用 `spine_restore_backup`，传 `dryRun:false`、`confirm:true` 和最新 `expectedHash`。
6. 恢复工具会先把当前错误 JSON 备份为 `*.before-restore.*.json`，再覆盖目标文件。
7. 调用 `spine_run_validation_pipeline`，并在 Spine 软件中确认导入。
8. 在恢复后的 JSON 上重新执行目标制作流程。
9. 将本次失败原因补充进官方规范审查层、测试和相关文档。

这条流程优先于“就地修补”。就地修补容易把多个问题叠在同一个文件里，导致后续难以判断到底是哪一次修改破坏了 Spine 导入。

## 备份工具返回字段

- `spine_list_backups.count`：匹配到的备份数量。
- `spine_list_backups.backups[].backupPath`：可传给 `spine_restore_backup` 的备份路径。
- `spine_list_backups.backups[].hash`：备份文件 hash。
- `spine_list_backups.backups[].validation`：备份 JSON 的结构校验结果。
- `spine_restore_backup.restoreSourceHash`：将要恢复的备份内容 hash。
- `spine_restore_backup.currentBackupPath`：真实恢复前保存当前目标文件的位置；dryRun 时为 `null`。
- `spine_restore_backup.summary.currentFileProtected`：真实恢复时是否已经保护当前目标文件。

## 返回字段说明

- `affectedPaths`：本次操作实际影响到的 JSON path，已去重，适合 Agent 快速判断修改范围。
- `diff`：完整差异条目，保留每一条具体修改；同一个 path 可能因为批量姿态写入出现多条 diff。
- `summary.operation`：执行的 MCP 工具名。
- `summary.diffEntryCount`：原始 `diff` 条目数量，用于判断本次事务实际产生了多少条差异记录。
- `summary.changedPathCount`：去重后的受影响 path 数量，和 `affectedPaths.length` 一致。
- `summary.changedTopLevelPaths`：主要影响的 JSON 子树，基于去重后的 path 统计。
- `summary.changedKeyframeCount`：估算受影响关键帧数量。
- `summary.wroteFile`：是否真实写入文件。
- `summary.nextStep`：建议下一步。
- `operationValidation.ok`：真实 diff 是否全部落在允许写入路径内。
- `operationValidation.rejectedPaths`：如果越权，这里会列出被拒绝的路径。
- `officialSpecValidation.ok`：当前可写 timeline 子集是否通过官方 JSON 规范审查。
- `officialSpecValidation.source`：规范来源链接。
- `officialSpecValidation.rulesApplied`：本次 JSON 中实际检查到的规则，例如 `bone.rotate`、`slot.attachment`。
- `officialSpecValidation.issues`：字段、类型、`curve` 或 `offsets` 不符合规则时的具体 path 和原因。
- `spine_run_validation_pipeline.ok`：提交后推荐验证流水线是否全部通过。
- `spine_run_validation_pipeline.structureValidation`：结构和引用校验结果。
- `spine_run_validation_pipeline.runtimeValidation`：官方 `spine-core` 加载验证结果。
- `spine_run_validation_pipeline.previewUrl`：可直接打开的浏览器预览链接。

## 禁止绕过

- 不要让 Agent 直接自由编辑 JSON 文件。
- 不要跳过 `dryRun` 直接写原始样本。
- 不要在没有 `expectedHash` 的情况下连续多步提交。
- 不要把一段完整新动画拆成大量连续提交；应优先用 `spine_apply_pose_sequence` 一次事务预览和提交。

- 不要绕过 MCP 自由写入 Spine JSON；Agent 和未来 Skill 都必须走 MCP 写入工具和官方规范审查层。

- 不要用普通文件复制绕过恢复工具覆盖目标 JSON；恢复也应走 `spine_restore_backup`，以保留二次备份和 hash 审查。

## 比较策略升版与失效范围

`comparisonPolicy` 升版（v2 → v3）会改变 `policyFingerprint`，连带使全部历史比较报告、修正报告与姿态审查失效。这是预期行为，不是可以绕过的兼容问题：旧报告不能当作当前批准，必须重跑 `spine_compare_pose_graphs` 并重新视觉审查。

比较报告的过期判定改用 `comparisonFingerprint`，只绑定 `version/policyFingerprint/ok/poseFingerprint/referenceFingerprint/visualRigFingerprint/sequenceFingerprint` 与各指标的 `id/required/status/error`；`message`、`uncertainties` 等展示字段变化不再触发失效，但任何判据变化仍会。

参考标注版本同样参与门禁：v1 参考不能与 v3 策略比较，必须先升级并补全 face/轮廓/朝向/前后证据。

## 角色文件写入锁

同一角色 JSON 在同一时刻只允许一个写入事务，锁文件位于工作区 `.spine-mcp/locks/{sha256(绝对路径)}.lock`。

- 锁记录写入 `pid`、`filePath`、`startedAt`，用于事后判断持有者。
- 争用时报错固定以「角色文件正在被其他任务修改」开头，并附带锁记录和锁文件路径。
- 清理是 best-effort：`close`、`unlink` 失败不会覆盖本次业务结果，也不会把异常抛给调用方；清理失败留下的锁不会自动回收。
- 残留锁沿用人工流程：先按锁记录中的 `pid` 核对进程是否已退出，确认后再删除锁文件重试；不要在没有核对的情况下批量清空锁目录。
- 进程被强杀会遗留锁，这是设计取舍，不是可以自动抢锁的理由。

`spine_retarget_motion` 新增 `diagnosticPreview:true`，仅支持 `dryRun`。用户要求观察整段失败候选时，可在保留未确认姿态和失败报告的前提下生成完整诊断动画：候选 JSON、实际关键时间关系比较、固定相机上下姿态图和目标原速 GIF。通过 `spine_render_animation_comparison` 生成上下同步 GIF。

诊断结果始终为 `ok:false`、`diagnosticOnly:true`、`readyToCommit:false`，分别返回 `numericOk`、`poseGate`、`keyGraphs` 和 `previewIssues`，不产生 `reviewToken`，不修改原角色。它是观察失败的独立出口，不能替代正式姿态/动画审查或用于提交。`diagnosticPreview:true,dryRun:false` 必须拒绝；渲染失败仍保留候选与错误。

实际验证脚本：`scripts/acceptance-animation-diagnostic.mjs`。先执行 `references`，Agent 查看参考连线图并填写逐阶段参考判断后执行 `animate`。脚本通过实际 MCP stdio 求解和渲染，仅创建工作流草稿，不自动批准任何目标姿态或完整动画。环境变量 `ANIMATION_DIAGNOSTIC_DIR` 可指定已有实例相对目录。

中文负例：把手目标设到骨骼不可达范围，再请求完整动画诊断。预期得到失败报告及 GIF、原 JSON 哈希未变、无提交令牌；请求真实写入仍应拒绝。不要把 GIF 生成成功描述为动画匹配通过。

## 解剖持杖手、身体视角及切片遮挡检查

参考 observation.actionSemantics 支持 `version:1 / weaponHand:left|right / identityStatus:confirmed / anatomicalBasis / bodyView / bodyViewBasis / occlusion`。身体视角可为 `frontThreeQuarter`、`side`、`backThreeQuarter`，参考有不确定性时可用 `sideOrBackThreeQuarter`。遮挡项保存 `{front,back,basis}`，语义部位可为 `body` 或已有肢体线段编号（如 `rightArm.1`）。缺少必要遮挡关系返回无法验证，不默认为通过。

`spine_calibrate_visual_rig` 增加 `anatomicalSides` 与 `viewProfiles`，均绑定确认指纹。解剖左右映射保持跨阶段稳定；视角配置保存实际附件状态、躯干插槽和看图校准依据。姿态 `frame.action.driver` 明确实际目标驱动手（如 `rightHand`），骨架比较独立输出 `action.weaponHand`、`action.bodyView`、`action.occlusion.*`。身体视角从 runtime 实际附件配置匹配已确认 profile；未经校准不能只传一个“背面”标签通过。遮挡用 runtime 绘制顺序回读。Agent 判断仍参与视角配置校准，这不是自动像素识别或数学上的视觉保证。

`frame.presentation` 支持受控 `attachments` 和完整 `drawOrder` 插槽排列，沿用 `spine_adjust_pose`、`spine_solve_pose` 和 v2 motion。显示状态在阶段边界离散切换，导出为已有 attachment/drawOrder 时间线；不改 setup、绑定、mesh、atlas 或 PNG。现有后发、面部显隐及背包层序可构造转身诊断候选，但不代表有完整三维转身模型。需要逐姿态查看轮廓并重新校准，不能自动批准隐藏五官后的身体视角。

中文验证：右手参考对应左手驱动必须失败；正面配置不能覆盖侧背参考；缺失视角/遮挡信息必须无法验证；同一附件状态不能标记成两种不同视角；遮挡层序反转必须失败。切片状态修改使配置匹配和旧审查失效。官方 runtime 回读 attachment/drawOrder 的阶段切换必须与单姿态一致。

## 准备姿态的新门禁

参考动作需有效动作级 sequence、已校准肩髋躯干轴和同一解剖对应。必要节点未知、身份冲突、侧背配置未校准、比较超差或视觉退回均阻止批准和正式写入。修正保存新修订，旧比较及审查不继承；reviewToken 仍受既有安全事务约束。失败候选可从 diagnosticPreview 出口导出副本，但没有提交令牌。默认 dryRun 的适配和修正不落盘。

2026-10-10 的 npc1 已被独立视觉审查退回，即使全部必要节点指标通过也不予写入。详见 [闭环说明](准备姿态适配与修正闭环.md)。

## 0.2.0 协议、缓存和任务控制

所有 MCP 调用先按公开 inputSchema 校验，未知顶层字段拒绝；姿态 frame/weapon/patch 使用同源嵌套 schema，禁止注入 solution/review 或原型字段，非有限数在写入前拒绝。部分 patch 仍深合并成新修订，清除旧求解与审查；领域层继续验证角色能力、引用及数值，schema 通过不代替审查。

缓存只复用文档解析、SkeletonData 和解码图像，每次求解使用独立 Skeleton。默认严格读取真实字节；requireReviewedPose、reviewPose、reviewAnimation、confirmMapping、reviewVisualRig、requirePoseComparison、refinePoseData 七个门禁强制 strict，即使外层显式选择 fast。相同文件大小和 mtime 不证明证据未变。只读 digestOk 只说明适用证据新鲜，不是提交授权。

长任务在求解采样、逐次修正、逐页/逐帧渲染和 runtime 验证的检查点处理取消。已完成的 Host patch 保留新版本；取消求解可能留下无派生结果的版本，须查询 state 后重新求解。资产事务开始前检查取消，进入原子发布后以明确回执及 journal 裁决，不声称自动回滚已完成提交。

工程切换由 MCP 顺序协调：旧 Host 停收新修改，等待在途操作及 journal 写入，释放写入锁并退役发现文件。收到 shutdown 的 202 后还要确认服务不可达、发现文件已撤销且锁已释放；超时、遗留锁或身份变化阻止新工程连接，不因超时接管。只读 resource 探测不会触发切换或自动启动 Host。
