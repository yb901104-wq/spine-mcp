# 点状骨骼位移透视方案

> **状态：方案（未实施）。** 提出于 2026-11-03，源于用户提出的真人 2D 骨骼动画工业做法。本文档是设计提案，尚未产生任何代码、MCP 工具或写入能力变更。落地前必须先决策"是否突破 V1 写入边界"（见§6）。

## 1. 背景：现有 scale 方案的三个缺口

现有单臂透视（见 [身体部件观测与透视缩放](身体部件观测与透视缩放-20261025.md) 与 `src/perspective.ts`）用**局部骨骼缩放**模拟空间透视，实测与代码核查暴露三个结构性问题：

1. **缩放沿父链继承，污染下游。** scale 会传递给子骨骼，代码只对链内第三段（手）做了末端补偿（`perspective.ts:107`），**手以下的下游节点（手指、持握物）不会被补偿**，会被连带缩放。
2. **与 IK / 约束不能共存。** 一旦臂链被 IK、transform 或 path 约束接管，直接拒绝（`perspective.ts:45-46`、`:96`），功能不可用而非降级。
3. **公式是迭代近似，收敛无保证。** 用 `boundedLeastSquares`（LM 风格）求解局部 scale，可能出现 `localStall` 或 `iterationLimit`；历史记录中 0.8/0.7 曾 33 次迭代停滞、手目标误差 4.39 未通过。之所以未失控，靠的是**窄范围门禁 + 逐样本真实 player 截图 + 33 帧连续性诊断 + 五项人工审查**四道外部闸门，而不是公式本身可控。

## 2. 机制：用位移制造透视，而不是用缩放

### 2.1 骨骼层级

在每段肢体的末端挂一个**点状子骨骼**（length 为 0 的 helper bone），下一段肢体绑定在它之下：

```
大臂(upperArm) → P1(点状) → 小臂(lowerArm) → P2(点状) → 手掌(hand)
```

### 2.2 位移如何产生"视觉缩放"

每段肢体的 mesh 同时绑定**该段骨骼**与**其末端的点状骨骼**，两者之间做平滑权重过渡。令点状骨骼沿肢体轴向**向根部方向**平移 Δ：

- 该段肢体在视觉上**缩短**（mesh 顶点随权重点重新分布）；
- **子级部件只是整体平移，自身世界长度与缩放完全不变**。

这正是"利用位移制造缩放感，但不像正常缩放那样影响后面的子骨骼"的原理。

### 2.3 与 scale 方案对比

| 维度 | 现有 scale 方案 | 本方案（点状骨骼位移） |
|---|---|---|
| 实现手段 | 改 `bone.scaleX / scaleY` | 改 point bone 的 `translate` |
| 子骨骼是否被污染 | 是，需末端补偿，下游未覆盖 | 否，位移不传递缩放 |
| 与 IK / 约束共存 | 必须拒绝 | 可共存（IK 使用 `bone.length`，不读 scale） |
| 公式 | 迭代近似，收敛无保证 | **闭式** `L′ = L·cos θ` |
| 对资产的要求 | 无特殊要求 | **必须 mesh + 权重绑定** |
| 是否需改 setup | 否 | 是（若资产本不具备结构） |

## 3. 公式与坐标约定

### 3.1 基本公式

设肢体真实长度为 `L`，肢体轴向与**画面平面**（垂直于视线的平面）的夹角为 `θ`：

```
L′ = L · cos θ        θ = 0° 平行画面 → 满长；θ → 90° 指向纵深 → 趋近 0
Δ  = L · (1 − cos θ)  位移量，方向沿肢体轴指向根部
```

`cos θ ≤ 1` 天然满足"透视感的边长不超过部件原本长度"这一约束。

### 3.2 数值对照

| θ | cos θ | L′/L | Δ/L |
|---|---|---|---|
| 0° | 1.0000 | 1.0000 | 0.0000 |
| 15° | 0.9659 | 0.9659 | 0.0341 |
| 30° | 0.8660 | 0.8660 | 0.1340 |
| 45° | 0.7071 | 0.7071 | 0.2929 |
| 60° | 0.5000 | 0.5000 | 0.5000 |
| 75° | 0.2588 | 0.2588 | 0.7412 |
| 90° | 0.0000 | 0.0000 | 1.0000 |

### 3.3 坐标系约定（必须显式确认，不得假设）

1. **位移施加在父骨骼的局部坐标系中**，沿该骨骼的**长度轴**，方向指向父骨骼原点。
2. Spine 绑定中骨骼长度轴**多数为局部 +x，但不保证**。实施前必须读取该骨骼的 setup 姿态并确认长度轴，不能按约定硬编码。
3. 若父骨骼存在旋转或非等比缩放，Δ 必须在局部系换算后再写入，不能直接当作世界位移。

### 3.4 θ 的来源（与项目一贯原则一致）

**θ 是创作意图输入，不是推断结果。** 与现有透视方案一致，MCP 不得从单张图片自动推断深度或前后关系。θ 由 Agent 依据已审查的参考与姿态意图显式给出，并在记录中保存依据文本（对应现有 `basis` 字段的语义）。

## 4. 资产前置条件清单

本方案**不要求 MCP 创建结构**，而是要求输入角色预先具备。实施时应提供只读校验，缺项明确拒绝并给出原因：

| # | 条件 | 可否机检 | 缺失后果 |
|---|---|---|---|
| 1 | 每段肢体末端存在点状子骨骼，且下一段绑定其下 | 可 | 无挂点，位移无法传递 |
| 2 | 点状骨骼 `length` 为 0（或可忽略） | 可 | 可能不是 helper bone |
| 3 | 肢体组件为 **mesh 附件**，顶点同时受该段骨骼与点状骨骼影响（权重 > 0） | **不需机检（资产前置，由制作方保证；首次截图即可发现，见§4.2）** | **纯 region 附件下位移只会整体平移，导致部件重叠或断裂，视觉上不产生缩短** |
| 4 | 权重在两段骨骼之间为平滑过渡分布 | 难（可给出分布统计供人工判断） | 过渡处出现硬折或撕裂 |
| 5 | 骨骼长度轴已确认（见§3.3） | 可 | 位移方向错误 |
| 6 | 该链若被 IK 接管，需事先约定目标同步策略（见§7） | 可（检出即提示） | 手偏离目标点 |

> 实测当前样本 `example-json/xiaoren.json`：95 根骨骼、15 根 `length=0`，但**皮肤附件类型只有 region，没有 mesh**。即当前样本**不满足条件 3**，不可直接套用本方案。

### 4.1 点状骨骼如何被识别与声明

**结论：不强制特殊命名。** 采用三层机制，**只有显式声明层具有授权效力**。

| 层 | 机制 | 是否授权 | 说明 |
|---|---|---|---|
| L1 显式声明 | 在 mapping 中新增字段声明点状骨骼，经既有 `spine_confirm_mapping` 确认后生效 | **是** | 权威来源，与项目现有"确认结果是真实写入门禁"的原则一致 |
| L2 命名约定 | 符合约定后缀（如 `_depth`）时作为**候选提示** | 否 | 仅加速发现，必须回到 L1 确认 |
| L3 结构机检 | `length=0` + 为目标骨骼子级 + mesh 权重受其影响 | 否 | 仅用于校验 L1 声明是否成立、以及反查遗漏 |

**为什么不给命名约定授权。** 三条理由：

1. **会破坏既有资产。** 美术已完成的角色不会为适配某个工具而改名，强制命名等于要求所有输入资产返工。
2. **Spine 生态不存在该约定。** 点状骨骼在 Spine 里通常叫 helper / IK target / 或干脆是美术自定义名，没有可依赖的行业惯例。
3. **同名与误判风险。** 按名字自动识别，遇到重名、不规范名或名字与职责不符（名字像控制点但实际是武器挂点）时会静默产生错误位移——与本文档反复强调的"静默错误"属同一类风险。

项目已有先例支持这一取向：`AGENTS.md` 明确"骨骼原点只作候选，需切片依据才能确认视觉关节"，即**不接受自动确认**。

**真正的解决方案是语义映射，不是命名。** 大模型不需要记住骨骼全名（如 `bone3`），只需引用 mapping 里的语义键。现有 mapping 已提供该能力（Agent 用 `leftArm` 而非 `"bone3","bone4","10"`），透视控制点沿用同一模式即可：

```json
"perspectivePoints": {
  "leftArm":  { "upper": "<大臂末端点状骨骼名>", "lower": "<小臂末端点状骨骼名>" },
  "rightArm": { "upper": "...", "lower": "..." }
}
```

**与现有 `bones.leftArm` 保持独立，不合并。** 现有 `leftArm` 是三段真实骨骼链，`perspective.ts:41` 依赖 `chain.length === 3`；把点状骨骼并入会破坏既有 scale 方案与映射语义。

**建议的命名约定（供人工制作资产时参照，非强制）：** `<段名>_depth`，如 `upperArm_depth`、`lowerArm_depth`。若资产恰好遵循，L2 可直接给出候选，减少人工确认成本。

**额外校验项：** 声明时需记录该点状骨骼是否**专用**。若它同时承担 IK target、武器挂点或附件绑定，位移会产生连带副作用，此类骨骼应拒绝用于透视控制（或要求显式声明副作用已评估）。

### 4.2 不能依赖大模型自行识别：当前系统缺少客观核对手段

**问题。** 本方案对骨骼与骨骼组的处理是"特殊"的（点状骨骼、mesh 权重、三段链、透视控制点）。能否指望大模型精准找到并正确使用这些结构？

**结论：不能。而且当前的短板不只是"模型可能找错"，而是"系统没有提供让模型核对的手段"。**

#### 必须先区分两件事

| 阶段 | 问题 | 能否靠大模型 | 说明 |
|---|---|---|---|
| 发现 | 从角色里找出哪些是透视控制点 | **不可靠** | 命名、`length=0` 都只是启发式；模型可能自信地选中错误的骨骼 |
| 使用 | 在结构已被可靠声明的前提下施加位移 | 可以 | 只要声明正确，写入本身是确定的 |

因此风险并不在"模型会不会写错 Δ"，而在**声明阶段一旦错了，后面全部静默地错**。语义键（`perspectivePoints.leftArm.upper`）给了模型一种虚假的确定感——它看到字段存在就认为结构成立。

#### 实测暴露的硬缺口

核查当前 MCP 能力，结论是**§4 条件 3 的"可否机检"原本标为"可"是错的**：

```
含 mesh / weight / vertex 的 MCP 工具：无
spine_get_skins 返回：仅 { skinCount, slotCount, attachmentCount } 数量摘要
样本 skeleton-4.1.json 附件字段：x, y, rotation, width, height（region，无 vertices）
```

即：**当前 MCP 没有任何工具能查询"哪个 mesh 顶点受哪些骨骼影响、权重是多少"**。这意味着：

- 模型无法核对"这个点状骨骼是否真的控制着那片 mesh"；
- L3 结构机检的第 3 条（权重）**当前无法实现**；
- 文档§4.1 的 L1 显式声明因此**缺少客观校验**，退化成"人工口头保证"。

#### 设计原则：让系统枚举事实，让模型做选择题

不能让模型凭空"找"，而应由系统暴露客观事实、模型从候选中选择，判定权交给客观校验：

| 环节 | 手段 | 是否新增能力 |
|---|---|---|
| 枚举候选 | 列出 `length=0` 骨骼与父子关系 | 否（`spine_get_skeleton_hierarchy` 可覆盖） |
| 静态反验 | 声明的骨骼确实 `length≈0`、确为目标骨骼直接子级 | 否（现有能力） |
| 权重正确性 | **由资产制作方保证**，非 MCP 职责 | 否，不新增工具 |
| 视觉确认 | 首次 player 截图 + 独立审查（可发现权重缺失或错刷） | 沿用既有门禁 |

**视觉确认是最关键也最省的一环**：权重没刷或刷错时，位移后部件要么不动、要么撕裂，在首次截图里一眼可辨。它同时覆盖了"骨骼选错"与"权重没刷"两类错误，且不需要任何新工具。

#### 结论

- 单靠大模型：**不能**可靠完成。
- 靠"枚举候选 + 静态反验 + 视觉确认"：可行，**模型只负责提出假设，判定权归客观校验与人工审查**。

#### 权重不属 MCP 职责范围（重要澄清）

**权重绑定是资产制作阶段的工作，MCP 既不刷权重，也不把"权重查询能力"作为前置门槛。** 明确边界：

| 事项 | 归属 | MCP 是否介入 |
|---|---|---|
| 建立点状骨骼、刷 mesh 权重 | **资产制作方** | 否（见§6，属 V1 禁写区） |
| 验证权重是否刷对 | 资产方自测 + 首次视觉确认 | 否，不新增专用工具 |
| 施加位移、出图供人看 | MCP | 是 |

理由：这类问题（骨骼建了但权重没刷，或刷错区域）在**首次 player 截图里一眼可见**——部件要么不动、要么撕裂。**不为"人眼一次就能发现的问题"新增专用只读工具**；用既有的视觉审查门禁覆盖即可，成本更低也更符合"资产前置"的分工。

> 若将来实践中确实频繁出现"声明正确但权重缺失"的误判，再考虑补一个只读的权重/顶点影响查询作为辅助诊断，**不作为本方案的前置门槛**。
>
> 本小节同时修正了§4 条件 3 的机检标注（原为"可"，实为"否"）；并**收回**了先前"必须先补齐 mesh 权重查询能力"的门槛设定。

## 5. 与现有 scale 方案的关系：并存，但严格互斥

建议**并存而不用一套机制混用**，理由与规则：

1. **不废弃现有方案。** npc1 的 0.85–1 范围已有真实批准记录、连续性诊断与官方导入证据，历史结论保留不改写。
2. **语义互斥。** scale 语义（`frame.perspective` 的 upper/lower/localScaleBounds）与位移语义是两种不同机制，同一肢体同时施加会叠加且不可控。
3. **独立字段。** 位移透视应独立成与 `frame.perspective` 平级的字段，实施时加互斥校验：同一肢体同一帧不得同时声明两种透视。
4. **准入判断。** 资产满足§4 条件时优先用位移方案；不满足时沿用 scale 方案并保留其全部既有门禁。

## 6. 需要突破的边界（关键决策点）

`AGENTS.md` 第 26 条：V1 只修改动画时间线，**不修改 setup pose、bones、slots、skins、mesh/deform、constraints 和 events**。

| 若要求 | 是否需突破边界 | 建议 |
|---|---|---|
| MCP 自建点状骨骼 | 需放开 `bones` 写入 | **不建议**。属结构变更，风险高且超出"动画时间线"范畴 |
| MCP 刷 mesh 权重 | 需放开 `skins` / `mesh` 写入 | **不建议**。刷权重本质是美术工作，不应由 MCP 代做 |
| 仅写点状骨骼的 translate 关键帧 | **不需要** | **推荐**。完全落在现有 V1 白名单内，`spine_set_bone_keyframe` 现成可用 |

**推荐定位：资产约定 + 动画写入 + 只读校验。** MCP 负责校验资产是否具备结构、按闭式公式写入 translate 关键帧、记录 θ 依据；不负责造结构或刷权重。这样既不触碰 V1 红线，又同时拿到"闭式公式"与"不污染子骨骼"两个收益。

## 7. 未解决项与建议决策

以下每项给出建议与理由。**建议不等于已决策**：除第 2 项属概念澄清可直接采纳外，其余均需在有真实资产验证前保持保守默认。

### 7.1 IK 共存时的目标同步

**问题。** P1 平移会把小臂整体带走；若该链受 IK 约束，手会偏离目标点。

**候选做法与判断：**

| 做法 | 后果 | 判断 |
|---|---|---|
| A. 先位移，再解 IK | IK 会把末端拉回原目标点，**位移产生的透视被 IK 覆盖** | 不可取 |
| B. 把 θ 折算进 IK 目标距离 | 目标距离 `L′ < 2L`，IK 会**弯曲肘部**来适配，视觉上表现为"屈肘"而非"透视" | 不可取 |
| C. 施加位移透视期间该段不使用 IK | 位移独立生效，视觉正确 | **推荐** |

**建议：采用 C，且默认拒绝而非自动绕过。** 实施时检出该链被 IK / transform / path 约束接管，默认报错拒绝（与现有 scale 方案 `perspective.ts:45-46`、`:96` 的保守口径一致）；仅当调用方显式声明 `ikPolicy: 'bypass'` 且已确认该段在本次写入期间不依赖 IK 时才放行。**不在未验证前提供自动 bypass**——理由同 B：一旦 IK 参与长度求解，出来的就不是透视而是屈肘，属于不易察觉的视觉错误。

### 7.2 多段同时透视的累积顺序

**问题。** 大臂位移会改变小臂的世界位置，是否需要累积修正？

**建议：不需要累积修正，但必须按父→子顺序写入。** 理由：位移只传递**位置**，不传递**长度**。因此每一段的位移量只依赖**本段自身的 setup 长度 `L` 与本段自己的 `θ`**，与父段位移无关。父段位移改变的是子段的世界起点，不改变子段局部长度。

实施时按父→子顺序依次写入，是为了让世界坐标计算落在正确的基础上；若误以为要累积修正而叠加，反而会引入误差。此项属**概念澄清，可直接采纳**，写入实现时应在注释中写明该性质，避免后续维护者"修复"成累积。

### 7.3 θ 到实际视觉长度的映射校准

**问题。** 本文档的 θ 是概念定义。角色带斜视角、或相机为正交/透视不同时，`L′ = L·cos θ` 未必直接成立。

**建议：保留 `cos θ` 为默认，但增设显式校准系数并强制视觉确认。**

- 引入 `foreshorteningScale`（默认 `1.0`，即纯 `cos θ`），该系数属**校准结果**，需经真实资产校准后记录，不得由 Agent 随意填写。
- 无论系数取值如何，**首次在某角色上启用必须经真实 player 截图与独立视觉审查**，沿用现有"数值 / Agent 视觉 / runtime / 编辑器导入分别报告"的惯例。公式闭式**不减少任何一道视觉门禁**——闭式解决的是"可复现与可预测"，不是"视觉正确"。
- 明确记录：θ 是创作意图量，不等于真实三维深度角。

### 7.4 权重分布质量

**问题。** 过渡是否平滑取决于原始美术权重。

**建议：不纳入 MCP 职责，由资产制作方保证，首次视觉确认兜底。** 权重绑定（含过渡带是否平滑）属资产制作阶段的工作，MCP 既不刷权重、也不做权重校验，**不新增专用工具**。理由：① 越界且质量难以由工具保证；② 权重缺失或刷错在首次 player 截图里一眼可辨（部件不动或撕裂），用既有视觉审查门禁覆盖即可——**不为"人眼一次就能发现的问题"新增只读工具**。若实践中确实频繁出现"声明正确但权重缺失"的误判，再考虑补一个只读诊断作辅助，但不设为前置门槛。

### 7.5 尚无真实资产验证

**问题。** 当前工作区样本（`example-json/xiaoren.json`）皮肤附件**只有 region、无 mesh**，不满足§4 条件 3，方案未在任何真实角色上跑通。

**建议：把"取得满足条件的真实角色"设为实施前置门槛，在此之前不写实现代码。** 避免在无验证资产上构建空中楼阁。若一时无法取得真实角色，允许先在**合成夹具**上验证"公式换算与坐标系换算"这两项纯数值逻辑，但必须同时满足两条：合成夹具结论**仅覆盖数值，不作为美术角色视觉验收**；真实资产到位后必须重跑完整验证，不沿用夹具结论。此口径与项目既有"合成夹具不作为真实美术角色视觉验收"原则一致。

### 7.6 是否需要新增 MCP 工具

**问题（补充）。** 本方案是否需要新工具？

**建议：暂不新增。** 写入侧复用现有 `spine_set_bone_keyframe`（`timeline: 'translate'`）即可覆盖，无需新工具；校验侧若确有必要，可另行评估一个只读的结构校验入口。等§7.5 的真实资产到位、确认复用方案存在缺口后，再按项目规则（新增工具须同步 [MCP 操作清单](MCP操作清单.md)）立项。

## 9. 与现有三段链映射模型的冲突（重大）

### 9.1 冲突现象

为透视插入点状骨骼后，一只手臂的层级从

```
大臂 → 小臂 → 手          （现状，mapping.bones.leftArm = [大臂, 小臂, 手]）
```

变为

```
大臂 → P1 → 小臂 → P2 → 手
```

此时无论怎么填 `mapping.bones.leftArm`，现有体系都会报错。

### 9.2 代码证据

| 位置 | 约束 | 冲突表现 |
|---|---|---|
| `motionEngine.ts:89-91` | `chain[i]` 的 `parent` **必须等于** `chain[i-1]`，否则抛"不是连续骨骼链" | 填 `[大臂, 小臂, 手]` → 小臂的 parent 是 P1 不是大臂 → **非法** |
| `mappingTools.ts:50` | `chain.length !== 3` 抛错："必须明确指定上段、下段、末端三根骨骼" | 填 5 段或 `[大臂, P1, 小臂]` → **长度不符** |
| `perspective.ts:41` | `chain.length !== 3` | 同上 |
| `retargetEngine.ts:140` | `chain.length !== 3` | 同上 |
| `hostPosePatch.ts:69` | `chain?.length === 3 && chain[2] === anchor?.bone` | 同上 |

**结论：现有映射模型与透视结构互斥。** 不是"配置麻烦"，是**结构上无法表达**——连 `spine_calibrate_mapping` 都过不去，后续 confirm、retarget、motion 提取、pose patch 全部失效。

### 9.3 根因：表达力不足，不是 Spine 的限制

点状骨骼 `大臂 → P1 → 小臂` 是**合法的 Spine 层级**，问题出在项目侧。

根因是现有映射模型把两件事压扁成了同一棵树：

- **层级链**（谁带动谁）与**权重域**（哪片 mesh 受哪根骨骼影响）在 Spine 里本是同一棵树；
- 但点状骨骼的角色是**跨域共享控制点**——它必须同时属于上一段的权重域（让大臂 mesh 在末端收缩）和下一段的层级链（带动小臂整体平移）；
- 现有 `bones.leftArm` 三段连续链假设**只能表达其中一端**，无法表达"三段 + 两个跨域控制点"。

即：**是项目映射模型的表达力不足，不是方案本身不可行。**

### 9.4 解法选项

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A | 点状骨骼设为旁支，小臂仍挂大臂下 | 低 | **无效**——P1 不带动小臂，失去透视意义 |
| B | 用 transform constraint 驱动 | 中 | constraint 在 V1 禁写区，且 `perspective.ts:45` 拒绝被约束接管的链 |
| C | 改造现有链模型：允许声明式跳过控制点，链长度可变 | **高** | 需改 5 处硬依赖；影响 retarget、motion 提取、pose patch、host 动画全链路；回归面大 |
| D | **新增平行结构**：保留现有三段链不动，透视角色另走 `leftArm: { segments, depthPoints }` 新结构 | 中 | 两套并存，需类型判别；但**不触碰现有回归面** |

### 9.5 建议

**采用 D（平行结构），并明确这是架构级变更而非增量功能。**

理由：C 要动的是贯穿 retarget / motion / pose / host 的核心假设，回归风险与工作量都远超"加一个透视功能"的范畴；D 让现有能力保持零改动，新结构独立演进，即使失败也不影响主线。

同时必须正视：**在 D 落地前，本方案不具备实施条件**。当前状态应登记为"设计冲突已识别，待决策是否立项"，而不是"待实现"。

**前置决策问题（需产品优先级判断）：** 为透视能力去引入一套平行映射结构，是否值得？若答案为否，本方案应归档而非继续推进——因为它的收益无法覆盖对核心映射模型的改动成本。

### 9.6 打包映射 + 命名约定：冲突降级为小改动

§9.5 的成本估算基于"改造链模型"。若采用**段与透视点打包映射**，并配合资产方**自定义命名标准**，§9 的冲突可从"架构级变更"降级为"一处校验逻辑调整"。

#### 9.6.1 推荐数据结构：平铺映射表，不改现有链

**关键做法：保持 `mapping.bones.leftArm` 仍是三段字符串数组不变**，另加一张平铺的"段骨骼 → 透视点骨骼"映射表：

```json
"bones": {
  "leftArm": ["arm1", "arm2", "hand"]
},
"depthPoints": {
  "arm1": "arm1-toushipoint",
  "arm2": "arm2-toushipoint"
}
```

这样带来的好处：

| 现有约束 | 是否仍成立 | 说明 |
|---|---|---|
| `chain.length === 3`（4 处） | **成立** | `leftArm` 未被改动，仍是 3 段 |
| `chain[2] === anchor.bone`（`hostPosePatch.ts:69`） | **成立** | 末端仍是 `hand` |
| `chain[i].parent === chain[i-1]`（`motionEngine.ts:89-91`） | **需放宽** | `arm2` 的 parent 是 `arm1-toushipoint` |

即：**5 处硬依赖里只需改 1 处**，且改动是"允许 parent 是上一段所声明的透视点"，属局部放宽而非结构重构。

#### 9.6.2 连续性校验的最小改法

```
现有：  parent === chain[i-1]
改为：  parent === chain[i-1] || parent === depthPoints[chain[i-1]]
```

并保留约束：一个段最多声明一个透视点；透视点必须是该段骨骼的**直接子级**；透视点不得再声明自己的透视点（防止链式歧义）。

#### 9.6.3 命名标准的可行性（已验证）

资产方承诺命名标准（段骨骼 `arm1` → 透视点 `arm1-toushipoint`）后：

- **正向派生确定**：`段名 + 固定后缀` → 控制点名；
- **反向解析确定**（已实测）：以固定后缀为锚从末尾剥离即得段名。**即使段骨骼名本身含分隔符也成立**——实测 `foo-bar-toushipoint` → `foo-bar`、`juese-2-toushipoint` → `juese-2` 均正确反解。

命名标准应遵循三条原则：

1. **后缀在资产内唯一用途**：不得与美术命名习惯冲突。`toushipoint` 满足（美术不会用拼音命名骨骼）；应**避免** `-end`、`-tip`、`-末端` 这类可能已被用作普通骨骼名的词。
2. **段骨骼名本身不得以该后缀结尾**，否则反解歧义（需在校验中显式检出）。
3. **大小写规则统一**，避免 `Arm1-ToushiPoint` 与 `arm1-toushipoint` 的歧义。

> 命名标准解决的是"发现效率"，**不解决"是否正确"**。名字对了但 mesh 权重没刷，透视依然无效。因此 §4.2 的**行为反验（位移后回读顶点）不可省略**。

#### 9.6.4 对 §9.5 结论的修订

采用 9.6.1 的平铺映射表后，§9.4 的选项 D 成本**大幅下降**：不必新建平行结构，只需在现有 mapping 上增加一个可选字段 + 放宽一处连续性校验。相应地，§9.5 的"是否值得"问题，答案门槛明显降低。

剩余前置只剩**一项**：取得满足§4 条件的真实角色资产（§7.5）。权重相关能力已按§4.2 划归资产方，不再作为 MCP 侧前置。
